## 2. DOCX 구조에서 알아야 할 것

DOCX 는 ZIP 이고 본문은 `word/document.xml` 이다. 글자는 이렇게 들어 있다.

```xml
<w:p>                                  <!-- 문단 -->
  <w:pPr>…문단 서식…</w:pPr>
  <w:r><w:rPr/><w:t>매출 </w:t></w:r>   <!-- run: 서식이 같은 글자 조각 -->
  <w:r><w:rPr><w:b/></w:rPr><w:t>120</w:t></w:r>
  <w:r><w:t>억 원</w:t></w:r>
</w:p>
```

화면에서는 "매출 **120**억 원" 한 문장이지만 run 3개다. 서식이 같아도 맞춤법 검사·편집 기록(`w:rsid*`) 때문에 run 이 잘게 쪼개져 있는 경우가 흔하다.
그래서 **"120억" 을 찾으려면 run 을 이어 붙인 글자에서 찾고, 바꿀 때는 각 run 에 나눠서 반영**해야 한다.

글자 외에 문단 안에 섞여 나오는 것:

| 요소 | 뜻 | 2단계에서 |
|---|---|---|
| `w:tab`, `w:br`(줄바꿈), `w:cr` | 탭·줄바꿈 | 글자 `\t`, `\n` 으로 보여준다. 바꾸기 범위에 들어가면 지우거나 새로 만든다 |
| `w:noBreakHyphen`, `w:softHyphen`, `w:sym` | 특수 문자 | 보여주되, 바꾸기 범위에 걸리면 거절 |
| `w:hyperlink` 안의 run | 링크 글자 | 링크 **안에서만** 바꾸면 허용. 링크 경계를 넘으면 거절 |
| `w:fldSimple`, `w:fldChar`/`w:instrText` | 필드 (쪽 번호, 목차, 날짜) | 결과 글자는 보여주되 고치지 않는다 (걸리면 거절). Word 가 다시 계산하는 값이라 |
| `w:drawing`, `w:pict`, `w:object` | 그림·도형·글상자 | `￼` 같은 자리 표시로 보여주고, 바꾸기 범위에 걸리면 거절 |
| `w:footnoteReference` 등 | 각주 번호 | 자리 표시, 걸리면 거절 |
| `w:ins`, `w:del`, `w:moveFrom/To` | 변경 내용 추적 기록 | 🔍 아래 결정 3 |
| `w:sdt` | 콘텐츠 컨트롤 (양식 칸) | 안의 글자는 일반 글자처럼. 컨트롤 경계를 넘으면 거절 |
| `w:proofErr`, `w:bookmarkStart/End`, `w:commentRangeStart/End`, `w:lastRenderedPageBreak` | 길이 없는 표시 | 글자로 보이지 않음. 그대로 둔다 (바꾼 범위 안에 있으면 앞으로 옮겨 남긴다) |
| `mc:AlternateContent` | 새 Word 용 + 옛 Word 용 두 벌 | 글상자 등에 쓰인다. 2단계는 들어가지 않는다 (두 벌을 같이 고쳐야 해서) |

## 3. 라이브러리

### 추천: `python-docx` 를 쓰지 않고 ZIP + `lxml` 로 직접 고친다

| 방식 | 장점 | 단점 |
|---|---|---|
| **ZIP + lxml 직접** | 고친 XML 파일(`word/document.xml` 등)만 다시 쓰고, **나머지 ZIP 항목은 바이트 그대로 복사**한다. 원본 보존이 가장 좋다. `lxml` 은 이미 설치돼 있다 (명시적 의존성으로 추가만) | 문단·run 다루는 코드를 직접 짜야 한다 (어차피 run 에 걸친 바꾸기는 python-docx 도 지원하지 않는다) |
| python-docx | 문서 열기·저장·표 순회가 쉽다 | `paragraph.text = …` 는 run 을 다 지워 서식이 사라진다. 결국 run 처리는 직접 해야 한다. 저장할 때 읽어 들인 부분을 다시 직렬화한다 |

- python-docx 는 **테스트용 시험 문서를 만들 때만** 쓰는 것도 방법이다 (개발 의존성). 🔍 결정 5.
- XML 파싱은 외부 엔티티·네트워크를 막는다 (`resolve_entities=False`, `no_network=True`). 압축 폭탄은 업로드 때 이미 검사한다 (`formats.py`).
- XML 선언(`<?xml … standalone="yes"?>`)과 네임스페이스 선언을 원본처럼 유지해서 쓴다.

## 4. 글자 모델과 바꾸기 알고리즘

### 문단을 "글자 목록"으로 펼치기

문단 하나를 순서대로 훑어 글자마다 출처를 기록한다.

```
"매출 120억 원"
 매 출 _ 1 2 0 억 _ 원
 r1 r1 r1 r2 r2 r2 r3 r3 r3      ← 각 글자가 어느 run 의 어느 w:t 몇 번째인지
```

- `w:tab` → `\t`, `w:br` → `\n` 도 글자 하나로 넣는다.
- 고칠 수 없는 요소(그림·필드·각주 번호·링크 경계 등)는 **벽** 글자로 넣는다. 보기에서는 자리 표시로 보이고, 바꾸기 범위가 벽을 지나면 거절한다.

### 바꾸기: 달라진 부분만 고친다

`old_text` → `new_text` 를 통째로 지우고 새로 쓰면, 바꾸지 않은 글자의 서식까지 하나로 뭉개진다.
예) "매출 **120**억" 에서 "120억" → "135억" 을 통째로 바꾸면, 새 글자가 첫 run(굵게)을 따라가 "억" 까지 굵어진다.

그래서 **old/new 를 글자 단위로 비교(`difflib.SequenceMatcher`)해서 달라진 부분만** 고친다.

```
old: 1 2 0 억        new: 1 3 5 억
     = ≠ ≠ =              → "20" 만 "35" 로 (r2 안에서) → 굵게 유지, "억" 은 그대로
```

| 바뀌는 모양 | 처리 |
|---|---|
| 바꾸기 (같은 run 안) | 그 `w:t` 의 글자만 바꾼다 |
| 바꾸기 (run 여러 개에 걸침) | 첫 run 에 새 글자를 넣고, 나머지 run 에서 해당 글자를 지운다 |
| 넣기 | **바로 앞 글자의 run** 서식을 따른다 (문단 맨 앞이면 바로 뒤 글자의 run). ✅ 구현하며 다듬음: `old_text` **안의** 이웃 글자를 먼저 따른다 (링크 글자 맨 앞에 넣은 글자가 링크 밖으로 새지 않게) |
| 지우기 | 해당 글자를 지우고, 비게 된 `w:t` 는 지운다. run 에 다른 내용이 없으면 run 도 지운다 |

- 앞뒤 공백이 있는 `w:t` 는 `xml:space="preserve"` 를 붙인다 (Word 가 앞뒤 공백을 버리지 않게).
- 바꾼 범위 안의 길이 없는 표시(책갈피, 메모 범위)는 지우지 않는다. ✅ 구현: run 안의 글자만 고치고 run 사이의 표시는 건드리지 않아 제자리에 남는다 (옮기지 않아도 된다).
- 🔍 비교가 너무 잘게 쪼개지면(예: 문장을 전부 바꿈) 오히려 이상한 run 조각이 남을 수 있다. 같은 글자가 절반 미만이면 통째로 바꾸기로 한다 (구현하며 기준 확인).

### `old_text` 찾기

- 1단계와 같은 규칙: 문서 전체에서 **정확히 한 번** (또는 `replace_all`).
- 찾는 단위는 **문단 하나 안**이다. 문단을 넘는 `old_text` 는 거절하고 "문단마다 따로 고쳐라" 고 돌려준다 (문단 합치기·나누기는 5단계).
- `new_text` 에 `\n` 이 있으면: 🔍 결정 4 (줄바꿈 `w:br` 으로 넣을지, 거절할지).
- 같은 글자가 여러 문단에 있을 때 하나만 고치려면 `old_text` 를 길게 쓰거나, 수정에 `paragraph`(예: `"p12"`)를 줘서 그 문단 안에서만 찾게 한다.

## 5. 도구

새 도구를 만들지 않고 1단계 도구를 넓힌다.

### `view_document_for_edit` (DOCX)

문단마다 번호를 붙여 보여준다. 표 칸은 위치를 함께 적는다.

```
[p1] (제목 1) 2024년 하반기 영업 보고
[p2] 매출은 120억 원으로 전년보다 8% 늘었다.
[p3] (표1 1행 1열) 지역
[p4] (표1 1행 2열) 매출
[p5] (표1 2행 1열) 서울
[p6] (표1 2행 2열) 52억
[p7] 자세한 내용은 영업팀 위키를 참고한다. ￼
```

- 번호는 본문 순서(표 칸 안 문단 포함)로 매긴다. 1단계의 `[L12]` 처럼 **접두어는 `old_text` 에 넣지 말라**고 적는다.
- 스타일 이름(제목 1 등)과 표 위치는 에이전트가 위치를 이해하는 데 쓰는 참고 정보다.
- `￼` 는 그림·필드처럼 고칠 수 없는 자리. 범례를 결과 끝에 한 줄로 붙인다.
- 긴 문서는 1단계처럼 `start_line` 대신 🔍 `start_paragraph` 로 나눠 보여준다 (인자 이름을 형식마다 다르게 할지, `start` 하나로 합칠지).

### `edit_document` (DOCX)

1단계 입력을 그대로 받고, 선택 필드 하나를 더한다.

```json
{ "old_text": "120억", "new_text": "135억", "replace_all": false, "paragraph": "p2" }
```

- `paragraph` 는 DOCX 에서만 쓴다 (없으면 문서 전체에서 찾는다). ✅ 텍스트 형식에서 주면 무시한다 (어차피 정확히 한 번 규칙이 있어 엉뚱한 곳을 고치지 않는다).
- 결과 첫 줄에 새 document_id·파일 이름 (1단계 G 결정과 같게), 그 아래 바뀐 문단의 전/후.

### 거절하는 경우 (추가분)

| 경우 | 돌려줄 말 |
|---|---|
| `old_text` 가 문단을 넘음 | "문단 하나 안에서만 고칠 수 있다. 문단마다 따로" |
| 바꾸는 범위가 그림·필드·각주 번호·링크 경계에 걸림 | "그 자리에는 고칠 수 없는 요소가 있다. 범위를 좁혀라" |
| 변경 내용 추적 기록이 있는 문단 (결정 3 에 따라) | "변경 내용 추적 기록이 있는 문단은 아직 고칠 수 없다" |
| 암호·DRM 문서 | 업로드 때 이미 실패하므로 여기 오지 않는다 |
| 매크로 문서 (`.docm`) | 형식 확인에서 DOCX 로 받지 않는 것을 구현 때 확인 🔍 |

## 6. 수정본 저장과 다시 읽기

```
edit_document (DOCX)
  → 원본 확인 (1단계 load 와 같은 규칙: 대화·소유자·형식·상태)
  → MinIO 원본 바이트 → ZIP 열기 → 고칠 XML 부분만 lxml 로 파싱
  → 문단 펼치기 → 바꾸기 적용 (하나라도 실패하면 전부 취소)
  → 고친 XML 만 다시 쓰고 나머지 ZIP 항목은 그대로 복사 → 새 바이트
  → MinIO 저장 → documents 행 추가 (revision+1, created_by='agent')
  → 본문(content) 다시 만들기 (아래)
```

### 본문(`content`) 다시 만들기

텍스트 형식은 본문 = 원본이라 바로 `ready` 였지만, DOCX 의 `content` 는 xberg 파싱 결과(Markdown, 그림 OCR 포함)다.

- 🔍 결정 2 선택지:
  - (A) **업로드와 같은 파싱을 돌린다** (별도 프로세스, OCR 포함). 본문 규칙이 업로드와 똑같다. 그림이 많으면 수 초~수십 초 걸린다.
  - (B) 파싱하되 **도구가 끝날 때까지 기다린다** (A 를 기다리는 것). 끝나면 바로 `read_document` 가 새 내용을 읽는다. 대신 그 시간만큼 답변이 늦다.
  - (C) 원본의 `content` 를 문자열로 고친다. 빠르지만 Markdown 표·OCR 글자와 원본 글자가 1:1 이 아니라 어긋날 수 있다.
  - 추천: **(B) 기다리되 시간 제한**. 글자만 바꿨으니 그림은 그대로라 대부분 1초 안팎이다. 시간을 넘기면 수정본은 저장한 채 `processing` 으로 두고 "준비되면 읽을 수 있다" 고 돌려준다.

## 7. 검증

### 자동 테스트

| 종류 | 내용 |
|---|---|
| 단위 (XML 조각) | run 3개에 걸친 바꾸기, 굵은 글자 일부만 바꾸기(서식 유지), 넣기·지우기의 서식 상속, 빈 run 정리, `xml:space` |
| 단위 | 탭·줄바꿈, 하이퍼링크 안/경계, 필드·그림 걸침 거절, 책갈피 보존, 문단 넘는 `old_text` 거절 |
| 단위 | 표 칸·중첩 표 번호, `paragraph` 로 좁히기, `replace_all` |
| 왕복 | 고치지 않은 ZIP 항목이 **바이트까지 같은지**, 고친 문단 말고 다른 문단의 XML 이 같은지 |
| 통합 | 수정본 행·MinIO 객체, 다시 파싱한 `content` 에 새 글자가 있는지 |

### 실제 문서로 손 검증

- 시험 문서는 **Word(또는 한글·Pages)로 직접 저장한 DOCX** 를 쓴다. 코드로 만든 DOCX 는 run 이 깔끔해서 실제 문제(잘게 쪼개진 run, 맞춤법 표시, rsid)가 안 드러난다.
- `works/files/` 에 1단계 시험 파일(`meeting-notes.txt` 등)처럼 DOCX 시험 파일을 둔다: 제목·굵게 섞인 문장, 표, 링크, 쪽 번호 필드, 그림, 머리글이 있는 문서.
- 고친 수정본을 Word 에서 열어 "복구" 경고가 없는지, 바꾼 곳 말고 그대로인지 눈으로 본다. 🔍 Word 가 없으면 LibreOffice 로 열기 + PDF 로 바꿔 원본과 나란히 비교.

## 10. 고도화 후보

2단계 커밋(`fed0114`, `d037a6e`) 뒤, 문단 나누기를 시작하기 전에 "실제로 쓸만한 DOCX 편집 에이전트" 에 필요한 기능을 조사했다 (2026-11-24).
아래 우선순위는 조사 결과에 따른 **제안**이고, 고도화 설계를 시작할 때 확정한다.

### 10.1 다른 제품은 어떻게 하나

**Open WebUI 본체에는 기존 docx 를 고치는 기능이 없다.** 편집 기능은 자체 노트에 있고, docx 편집은 커뮤니티 도구로 붙여 쓰는 구조다.

| 제품 | docx 관련 기능 | 참고할 점 |
|---|---|---|
| Open WebUI 본체: 노트 | 자체 리치텍스트 편집기. 선택한 부분을 AI 가 그 자리에서 고쳐 쓴다(Enhance). 에이전트 도구는 `write_note`, `replace_note_content`(`replace_text` 로 일부 바꾸기) | ① AI 가 넣기 전에 **버전을 먼저 남기고** 되돌릴 수 있다. ② 모델이 읽은 뒤 바뀐 페이지는 **수정을 거절**한다. ③ 메모·공동 편집. docx 내보내기, 변경 추적, 비교 화면은 없다 |
| Open WebUI 본체: Open Terminal | AI 가 python-docx 코드로 **새** docx·pptx·xlsx 를 만들고 채팅에 미리보기·다운로드를 붙인다 | 기존 docx 수정은 없다. Word 파일은 미리보기만. 에이전트가 고친 파일은 diff 로 보여 준다 |
| 커뮤니티 도구 "Edit Office Files" | 함수 52개: 서식 지키는 찾아 바꾸기, 덧붙이기, **변경 추적으로 고치기(작성자 지정)**, 추적 수락·거절, **메모**, 템플릿·편지 병합, 머리글·목차·서명, 워터마크·보호·메타데이터, 문서 비교, 버전, MD·HTML 내보내기 | "Open WebUI 는 docx 편집이 된다" 는 인상은 대부분 이 도구에서 온다. 기능 목록 참고용 |
| 커뮤니티 도구 "Generate Documents" | Markdown·JSON → docx. 템플릿 7종, 표지·목차·표 스타일, 첨부 docx 의 **레터헤드(머리글·바닥글) 재사용** | 생성만. "회사 양식에 맞춰 만들어 줘" 에 해당 |
| Word Copilot | 만들기·고쳐 쓰기·서식·요약·재구성, 어조 바꾸기, **글 → 표**, 그림 넣기 | 선택 → **미리보기 → 바꾸기/아래에 넣기/다시 만들기**. 변경 추적이 켜져 있으면 **추적으로 남긴다**. 새 파일은 못 만든다 |
| ChatGPT (Word 추가 기능, DOCX 앱) | 스타일 지키는 고쳐 쓰기, 서식, **표 편집**, 쪽 설정, 고친 사본 내려받기 | 복잡한 서식·표·차트는 손으로 고쳐야 할 수 있다고 밝힌다 |
| Gemini in Docs | Refine, **원본 서식에 맞춰 만들기(Match doc format)**, 표 채우기(Fill with Gemini) | 원본 서식·구조에 맞추는 것을 핵심으로 내세운다 |
| Claude docx 스킬 | 만들기·고치기·분석, **변경 추적(`w:ins`·`w:del`, 작성자)**, 메모, 모두 수락 | 검토 작업에서는 추적·메모가 기본 동작 |

**공통점:** ① 글자 바꾸기를 넘어 **구조(문단·표)** 를 다룬다. ② 고친 내용을 **사람이 검토할 수 있게** 변경 추적·미리보기·메모로 보여 준다. ③ **새 문서를 서식에 맞춰 만든다.**
지금 우리는 ① 의 가장 기본(문단 안 글자 바꾸기)만 된다.

### 10.3 제안

- **순서:** ① 구조 기본 A1~A4 + C1 → ② 검토 흐름 B1~B3 → ③ 만들기 D1~D2 → ④ 서식·화면 E·F.
  실제로 막힌 요청이 구조 쪽이고, B1(변경 추적)은 업무용 경쟁 제품이 모두 갖춘 "믿고 쓰게 만드는" 기능이라서.
- **도구를 늘리지 않는다.** `edit_document` 의 수정 하나에 종류(`replace` / `insert_paragraph` / `delete_paragraph` / `split` / `table_row` …)를 붙여 넓힌다.
  모델이 고를 도구가 늘지 않고, "한 번 부르면 수정본 하나" 와 "전부 성공 아니면 취소" 규칙(C1 을 하면 이 규칙은 다시 정함)을 그대로 쓸 수 있다.
- 이 목록 밖이지만 한국 사용자에게는 **HWP·HWPX 수정**(원래 계획의 뒤 단계)도 체감이 크다.

| 묶음 | 한 줄 설명 | 지금 상태 | 다른 제품 |
|---|---|---|---|
| A. 구조 | 문단·표를 넣고, 빼고, 나누기 | ❌ 글자만 바꿈 | 대부분 됨 |
| B. 검토 | 고친 곳이 Word 에서 보이고 메모를 달 수 있음 | ❌ | Copilot·Claude·커뮤니티 도구 |
