# 02-1. DOCX 고도화: 쓸만한 Word 편집 에이전트

`02.docx.md`(2단계: DOCX 글자 바꾸기) 다음 작업. PPTX(3단계)로 넘어가기 전에 DOCX 편집을 실제로 쓸만한 수준까지 넓힌다.
이 문서는 **조사 결과와 고도화 범위·설계 방향**을 정리한다. 2단계 구현 코드(`backend/app/documents/editing/docx.py`)를 기준으로 썼다.

## 2. 조사: 다른 제품은 어떻게 하나

### 2.1 Open WebUI

**본체에는 기존 docx 를 고치는 기능이 없다.** "Open WebUI 는 문서 편집이 된다" 는 인상은 아래 세 가지가 섞인 것이다.

#### 노트 (Notes, 본체)

- 자체 리치텍스트 편집기. docx 파일이 아니라 앱 안의 문서다.
- 선택한 부분을 AI 가 그 자리에서 고쳐 쓴다 (Enhance).
- 에이전트용 도구: `write_note`(전체 쓰기), `replace_note_content`(`replace_text` 로 일부 바꾸기). **우리 `edit_document` 의 `old_text`/`new_text` 와 같은 방식**이다.
- 안전장치
  - AI 가 내용을 넣기 **전에 버전을 먼저 남긴다**. 되돌리기가 된다.
  - 모델이 읽은 뒤 내용이 바뀐 노트는 **수정을 거절한다** (stale read 방지).
- 메모(코멘트), 공동 편집이 된다.
- 없는 것: docx 로 내보내기 (사용자 요청이 discussion #20420 으로 올라와 있다), 변경 내용 추적, 비교 화면.

#### Open Terminal (본체)

- AI 가 샌드박스에서 python-docx 코드를 짜서 **새** docx·pptx·xlsx 를 만든다. 채팅에 미리보기와 다운로드를 붙인다.
- 기존 docx 를 고치는 사용 사례는 문서에 없다. Word 파일은 미리보기만 한다.
- 에이전트가 고친 파일(코드·텍스트)은 diff 로 보여 준다.

#### 커뮤니티 도구 "Edit Office Files"

함수 52개짜리 도구. 기능 목록으로 참고하기 좋다.

| 묶음 | 기능 |
|---|---|
| 글자 | 서식을 지키는 찾아 바꾸기, 끝에 덧붙이기 |
| 검토 | **변경 내용 추적으로 고치기 (작성자 지정)**, 변경 추적 수락·거절, **메모 달기** |
| 만들기 | 템플릿, 편지 병합(mail merge), 머리글·목차·서명이 든 문서 |
| 문서 속성 | 워터마크, 문서 보호, 메타데이터 |
| 관리 | 문서 비교, 버전 관리, MD·HTML 로 내보내기 |

#### 커뮤니티 도구 "Generate Documents"

- Markdown 이나 JSON 을 받아 docx 를 만든다. 생성만 한다.
- 템플릿 7종(보고서, 제안서, 회의록 등), 표지·목차·표 스타일.
- 첨부한 docx 의 **레터헤드(머리글·바닥글)를 재사용**한다. "회사 양식에 맞춰 만들어 줘" 요구에 맞는 기능이다.

### 2.2 Microsoft Word Copilot

- Edit with Copilot: 문서 안에서 만들기, 고쳐 쓰기, 서식, 요약, 재구성, 어조 바꾸기, **글을 표로 바꾸기**, 그림 넣기.
- 흐름: 선택 → **미리보기** → `바꾸기` / `아래에 넣기` / `다시 만들기`. 사용자가 고르기 전에는 문서가 바뀌지 않는다.
- Word 의 변경 내용 추적이 켜져 있으면 **Copilot 이 고친 것도 추적으로 남는다.**
- Agent Mode: 여러 단계에 걸친 문서 작업(구조 잡기, 여러 곳 고치기)을 대화로 한다.
- 새 파일은 만들지 못한다 (열린 문서 안에서만).

### 2.3 ChatGPT (Word 추가 기능, "View and edit DOCX files" 앱)

- 선택한 글을 **문서 스타일을 지키며** 고쳐 쓰기, 서식 적용, **표 편집**, 쪽 설정.
- DOCX 앱은 올린 파일을 고쳐 **고친 사본을 내려받게** 한다. 우리 수정본 방식과 같다.
- 복잡한 서식·표·차트는 손으로 고쳐야 할 수 있다고 도움말에서 스스로 밝힌다.

### 2.4 Google Gemini in Docs

- 선택한 부분 Refine(고쳐 쓰기), 어조·길이 바꾸기.
- **Match doc format**: 새로 만드는 내용을 원본 문서 서식에 맞춘다.
- Fill with Gemini: 표 칸을 채운다.
- 서식·구조를 원본에 맞추는 것을 핵심 기능으로 내세운다.

### 2.5 Claude docx 스킬 (Anthropic)

- 새로 만들기, 고치기, 분석.
- 고칠 때 **변경 내용 추적(`w:ins`·`w:del`, 작성자 지정)** 으로 남기는 것을 기본으로 권한다. 메모 달기, 모든 변경 수락.
- 문서 검토 작업에서는 추적·메모가 기본 동작이라는 근거.

### 2.6 참고 라이브러리

| 이름 | 쓸모 |
|---|---|
| `docx-revisions` (PyPI) | python-docx 위에서 변경 추적(`w:ins`/`w:del`) 읽기·쓰기. B1·B3 구현 참고 |
| `docx-mcp-server` (PyPI) | MCP 로 docx 편집 기능을 노출. 도구 나누는 방식 참고 |

우리는 ZIP + lxml 직접 방식(2단계 결정 5)이라 라이브러리를 그대로 쓰지 않고 XML 구조만 참고한다.

## 3. 공통 패턴과 우리에게 주는 교훈

| 패턴 | 어디서 | 우리 상태 |
|---|---|---|
| **구조(문단·표)를 다룬다** | Copilot, ChatGPT, Gemini, 커뮤니티 도구 모두 | ❌ 글자만 바꾼다 |
| **사람이 검토할 수 있게 보여 준다** (변경 추적, 미리보기, 메모, diff) | Copilot(추적·미리보기), Claude 스킬(추적·메모), Open WebUI(버전·diff) | △ 수정본·답변 요약뿐 |
| **새 문서를 서식에 맞춰 만든다** | Open WebUI(Terminal, Generate Documents), Gemini(Match doc format) | ❌ TXT·MD·CSV 만 |
| **고치기 전에 되돌릴 곳을 남긴다** | Open WebUI 노트 | ✅ 수정본이 새 행이라 원본은 그대로 |
| **오래된 내용을 고치지 않게 막는다** | Open WebUI 노트(stale read 거절) | ❌ 이전 수정본도 그냥 고친다 |
| **원본 서식을 지킨다** | 모든 제품이 내세움, 그러나 "복잡한 서식은 깨질 수 있음" 단서 | ✅ 2단계의 강점 (바꾼 글자 말고는 그대로) |

정리하면, 우리 에이전트는 **원본 보존은 경쟁 제품보다 낫지만 할 수 있는 일의 폭이 좁다.** 고도화는 폭을 넓히되 "바꾼 곳 말고는 그대로" 원칙을 지키는 방향이어야 한다.

### 4.2 A. 구조 고치기

지금 가장 자주 막히는 부분이다. 구조를 바꾸면 **문단 번호가 밀린다**는 공통 문제가 있다 (6.3절).

#### A1. 문단 나누기·합치기 (P0)

- 요청 예: "덩어리진 문단을 세 문단으로 나눠 줘", "이 두 문단을 하나로 합쳐 줘".
- 나누기: `new_text` 의 `\n` 자리에서 문단을 나눈다.
  - 새 문단은 원래 문단의 `w:pPr`(스타일·들여쓰기·번호)을 복사한다.
  - 나누는 자리에 걸친 run 은 둘로 쪼개고 `w:rPr` 를 양쪽에 복사한다.
  - `w:pPr` 안의 `w:sectPr`(구역 나누기)는 **마지막 조각에만** 남긴다. 복사하면 구역이 늘어난다.
  - 문단 ID(`w14:paraId`, `w14:textId`)는 문서 안에서 유일해야 하므로 복사본에서는 지우거나 새로 만든다.
  - 거절: 나누는 자리가 링크·콘텐츠 컨트롤·필드 안이거나, 변경 추적 문단이거나, 표 칸 경계를 넘을 때.
  - `\n\n`(빈 줄)은 문단 하나 나누기로 본다. 빈 문단을 만들지 않는다.
- 합치기: 뒤 문단의 run 을 앞 문단 끝으로 옮기고 뒤 문단을 지운다.
  - 앞 문단의 `w:pPr` 를 쓴다. 뒤 문단에 `w:sectPr` 가 있으면 거절한다 (구역이 사라짐).
  - 다른 표 칸·다른 부분(본문과 머리글)에 걸치면 거절한다.
  - `old_text` 가 문단 경계를 넘는 지금의 거절("문단마다 따로")을 합치기로 풀 수 있다.
- 🔍 `\n` 을 문단 나누기로 볼지 문단 안 줄바꿈(A6)으로 볼지 (9절 결정 2).

#### A2. 문단 넣기·지우기·옮기기 (P0)

- 요청 예: "결론 문단 하나 추가해 줘", "p7 은 빼 줘", "이 문단을 맨 앞으로".
- 넣기: `after: "p12"` 또는 `before: "p12"` 로 위치를 정한다.
  - 새 문단 서식은 **기준 문단의 `w:pPr` 와 첫 run 의 `w:rPr`** 를 따른다 (주변과 같은 모양). 제목 뒤에 넣는 본문이면 다음 본문 문단을 따르는 편이 자연스럽다 🔍.
  - 스타일을 직접 지정할 수 있게 한다 (E2 와 같은 스타일 이름표).
- 지우기
  - 표 칸(`w:tc`)에는 문단이 최소 하나 있어야 한다. 마지막 문단을 지우면 빈 문단을 남긴다.
  - `w:sectPr` 를 가진 문단은 거절하거나, 구역 정보를 앞 문단으로 옮긴다 🔍.
  - 책갈피·메모 범위의 시작만 지워지고 끝이 남지 않게, 지우는 문단 안의 `bookmarkStart`/`commentRangeStart` 짝을 같이 정리한다.
  - 그림·필드가 든 문단도 지울 수 있게 할지 🔍 (그림 관계는 남아도 Word 가 열 수 있다).
- 옮기기: 지우기 + 넣기. 같은 부분(본문 안) 안에서만.

#### A3. 표 행·열 넣기·지우기, 칸 채우기 (P0)

- 요청 예: "부산 행 추가", "합계 열 추가", "비고 열 지워 줘".
- 행 넣기: 기준 행(`w:tr`)을 복사하고 칸 안 글자를 비운 뒤 새 값을 넣는다. 칸 서식(테두리·배경·정렬)이 따라온다.
- 열 넣기: `w:tblGrid` 에 `w:gridCol` 을 넣고, 모든 행에 `w:tc` 를 넣는다. 표 전체 너비를 어떻게 나눌지 정해야 한다 🔍.
- 거절: 세로 병합(`w:vMerge`)·가로 병합(`w:gridSpan`)이 걸린 행·열. 처음에는 병합 없는 표만.
- 칸 채우기: 지금도 칸 안 글자는 바꿀 수 있지만 **빈 칸에는 `old_text` 가 없어 못 채운다.** 빈 칸(빈 문단)을 `paragraph` 로 지정해 글자를 넣는 방법이 필요하다.
- 보기에서 표를 행 단위로 묶어 보여 주면 에이전트가 행을 고르기 쉽다 🔍.

#### A4. 목록 항목 넣기·지우기 (P1)

- 회의록·기획서는 대부분 목록이다.
- 목록 문단은 `w:pPr/w:numPr`(`w:numId`, `w:ilvl`)로 번호를 갖는다. A2 로 같은 `w:numPr` 를 복사해 넣으면 **번호가 이어진다** (번호 글자는 Word 가 계산).
- 들여쓰기 수준 바꾸기는 `w:ilvl` 만 바꾸면 된다.
- 보기에서 목록 문단에 `(목록 2수준)` 같은 표시를 붙이면 좋다 🔍.

#### A5. 제목 단위(섹션) 옮기기·지우기·넣기 (P1)

- 요청 예: "2장과 3장 순서 바꿔 줘", "부록 빼 줘".
- 섹션 = 제목 문단부터 같은 수준 이상의 다음 제목 전까지. 제목 수준은 스타일(`Heading N`)이나 `w:outlineLvl` 로 안다.
- A2 의 여러 문단 버전이다. 표도 함께 옮겨야 한다 (문단만이 아니라 블록 단위).

#### A6. 문단 안 줄바꿈 넣기 (P1)

- `w:br` 를 run 안에 넣는다. 보기에서 지금도 `\n` 으로 보인다.
- 주소·서명처럼 "한 문단 안에서 줄만 바꾸기" 가 필요한 경우.

#### A7. 글 ↔ 표 바꾸기 (P2)

- Copilot 의 대표 기능. "이 목록을 표로 정리해 줘".
- 표를 새로 만드는 것이라 D1(만들기)의 표 생성 코드를 같이 쓴다.

### 4.3 B. 검토 흐름

업무용(계약서·보고서 검토)으로 쓰려면 필요하다.

#### B1. 변경 내용 추적으로 고치기 (P0~P1)

- Word 에서 "검토 → 변경 내용" 으로 하나씩 수락·거절할 수 있게 남긴다. 작성자는 "AI 에이전트" 🔍.
- 2단계의 diff 결과가 그대로 쓰인다.

```xml
<!-- "120억" → "135억" : 바뀐 부분 "20" → "35" 만 -->
<w:r><w:t>1</w:t></w:r>
<w:del w:id="101" w:author="AI 에이전트" w:date="2026-11-24T10:00:00Z">
  <w:r><w:rPr><w:b/></w:rPr><w:delText>20</w:delText></w:r>
</w:del>
<w:ins w:id="102" w:author="AI 에이전트" w:date="2026-11-24T10:00:00Z">
  <w:r><w:rPr><w:b/></w:rPr><w:t>35</w:t></w:r>
</w:ins>
```

- 지우기는 run 을 `w:del` 로 감싸고 `w:t` 를 `w:delText` 로 바꾼다. 넣기는 새 run 을 `w:ins` 로 감싼다.
- `w:id` 는 문서 전체(메모·책갈피와 별도로 변경 기록끼리) 유일해야 한다.
- 문단 나누기·넣기(A1·A2)도 추적하려면 문단 기호에 `w:pPr/w:rPr/w:ins` 를 단다. 처음에는 글자 바꾸기만 추적 🔍.
- 보기·찾기는 **추적을 수락한 모습**(ins 보임, del 숨김)으로 보여 준다. 지금 펼치기 규칙과 같다.
- 결정 3(추적 기록이 있는 문단은 거절)과 부딪친다. 우리가 남긴 추적 위에 다시 고치려면 이 거절을 풀어야 한다 (B3 과 함께).
- 켜고 끄는 방법 🔍: 도구 인자(`track_changes: true`), 사용자 설정, 원본에 `w:trackRevisions` 가 켜져 있으면 자동 (Copilot 방식).

#### B2. 메모 달기 (P1)

- "검토해 줘" 에 본문을 고치지 않고 의견만 남기는 방법. "이 수치는 근거가 필요합니다".
- 필요한 것
  - `word/comments.xml` 부분 (없으면 만들고 `[Content_Types].xml` override, `document.xml.rels` 관계 추가).
  - 본문에 `w:commentRangeStart` / `w:commentRangeEnd` + `w:commentReference` 를 가진 run.
  - 메모 `w:id` 유일, 작성자·날짜.
- 범위는 `old_text` 로 정한다 (찾기 규칙 그대로). 도구는 `edit_document` 의 수정 종류 `comment` 로 🔍.

#### B3. 기존 변경 추적 읽기, 수락·거절 (P1)

- 남이 검토한 문서를 올리면 지금은 그 문단을 아예 못 고친다.
- 보기에서 추적 내용을 보여 준다: `[p5] 매출은 {-120-}{+135+}억 원` 같은 표시 🔍.
- 수락: `w:ins` 를 벗기고 `w:del` 을 지운다. 거절: 반대. `w:moveFrom`/`w:moveTo`, 서식 변경(`w:rPrChange`, `w:pPrChange`)도 처리해야 한다.
- 범위: 문서 전체 수락·거절부터, 문단·작성자 단위는 나중에 🔍.

#### B4. 화면에서 원본·수정본 비교 (P1)

- Open WebUI 도 에이전트가 고친 내용을 diff 로 보여 준다. 지금은 답변 텍스트의 바뀐 글자 요약뿐이다.
- 도구 결과에 이미 바뀐 문단의 전/후가 있다. 이것을 구조화해 프런트에서 문단 단위 diff 로 그린다.
- 프런트 작업이 크다. F1(미리보기)과 같이 설계 🔍.

### 4.4 C. 문서 전체 작업

#### C1. 많이 고치기, 부분 실패 보고 (P0)

- "맞춤법 다 고쳐 줘", "'고객사' 를 '고객' 으로 통일" 처럼 수정이 수십 개면, 지금 규칙(하나라도 실패하면 전부 취소)에서는 한 번의 실수로 전부 날아가 재시도가 반복된다.
- 바꿀 규칙 🔍
  - (A) 성공한 수정만 적용해 수정본을 만들고 실패한 수정은 이유와 함께 돌려준다.
  - (B) 지금처럼 전부 아니면 취소, 대신 실패 목록을 한 번에 다 알려 준다 (첫 실패에서 멈추지 않음).
  - (C) 인자로 고른다 (`atomic: true` 가 기본).
  - 추천: **(A) 를 기본으로, 하나도 성공하지 못하면 수정본을 만들지 않는다.** 에이전트가 실패한 것만 다시 시도하면 된다.
- 문단 번호(`pN`)는 호출을 시작할 때의 번호로, `old_text` 는 앞 수정을 적용한 글자에서 찾는다 (9.1절에서 확정).

#### C2. 보기에서 찾기 (P1)

- 긴 문서(100쪽 이상)를 400문단씩 넘겨 보면 토큰과 시간이 많이 든다.
- `view_document_for_edit` 에 `query` 를 더한다: 글자가 든 문단만 문단 번호와 함께, 필요하면 앞뒤 한 문단씩.
- 텍스트 형식(TXT·MD·CSV)에도 같이 쓸 수 있다 (줄 단위).

#### C3. 문단 고쳐 쓰기에서 서식 유지 (P1)

- 번역·어조 바꾸기처럼 문단이 거의 다 바뀌면, 결정 8(같은 글자 절반 미만이면 통째로)에 따라 새 글자 전체가 첫 조각 서식을 따른다. 문단 안의 굵은 단어·링크가 사라질 수 있다.
- 개선 방향 🔍
  - 글자 대신 **낱말 단위 비교**로 바꿔 살아남은 낱말의 서식을 지킨다.
  - 서식 있는 조각(굵게·링크)이 새 글에도 그대로 나오면 그 자리에 서식을 다시 입힌다.
  - 에이전트가 서식을 표시해 보내게 한다 (예: `**135억**`). E1 과 겹친다.
- 링크 안 글자가 통째로 바뀌는 경우는 지금도 링크 경계 규칙으로 막힌다.

#### C4. 최신 수정본 확인 (P1)

- 수정본이 쌓이면 에이전트가 v2 를 고친 뒤 v1 을 또 고쳐 갈래가 생길 수 있다.
- 고치려는 문서보다 **revision 이 큰 수정본이 같은 대화에 있으면** 거절하거나 경고하고 최신 document_id 를 알려 준다 🔍.
- Open WebUI 노트의 "읽은 뒤 바뀐 페이지는 거절" 과 같은 목적. 구현이 쉽다 (서비스에서 조회 한 번).

### 4.5 D. 만들기 (원래 7단계)

#### D1. Markdown → 새 docx (P0)

- Open WebUI(Terminal, Generate Documents)의 핵심 기능이다. 지금은 "Word 로 만들어 줘" 에 MD 를 권한다.
- 넣을 것: 제목 1~3, 문단, 굵게·기울임·링크, 글머리표·번호 목록, 표, 인용, 쪽 나누기.
- **한글 글꼴**: `w:rFonts` 의 `w:eastAsia` 를 맞춰야 한다 (2단계 시험 문서에서 OpenSymbol 로 잡혀 깨진 경험).
- 방법 🔍
  - (A) 빈 기본 템플릿 docx(스타일·번호 정의만 든 것)를 저장소에 두고, 본문 XML 만 lxml 로 만들어 넣는다. 2단계 코드와 같은 방식, 의존성 없음.
  - (B) python-docx 를 생성용으로만 넣는다 (2단계 결정 5 는 편집용 기준).
  - (C) Pandoc 같은 외부 변환기. 이미지가 커지고 운영 부담.
  - 추천: **(A)**. 목록 번호(`numbering.xml`)와 표 스타일을 템플릿에 미리 정의해 두면 본문만 만들면 된다.
- 기존 `create_document`(1단계, TXT·MD·CSV 만들기)에 형식 `docx` 를 더하는 방향.

#### D2. 양식·템플릿 채우기 (P1)

- 한국 업무 문서는 양식이 정해진 경우가 많다 (품의서, 회의록, 보고서 양식).
- 두 가지
  - **자리 바꾸기**: 양식 안의 `{{이름}}` 같은 자리를 값으로 바꾼다. 자리 글자가 run 여러 개로 쪼개져 있어도 2단계 펼치기로 찾을 수 있다. 사실상 `replace_all` 묶음이다.
  - **양식 위에 본문 쓰기**: 올린 docx 의 머리글·바닥글·스타일을 그대로 두고 본문만 D1 처럼 채운다 (Generate Documents 의 레터헤드 재사용).
- 표 행을 값 개수만큼 늘리는 경우(품목 목록)는 A3 행 넣기를 쓴다.

#### D3. 다른 형식으로 내보내기 (P2)

- DOCX → PDF, DOCX → MD. PDF 는 서버에 LibreOffice + 한글 글꼴이 필요하다 (이 맥의 headless LibreOffice 는 한글을 그리지 못했다. 컨테이너에서는 글꼴 패키지를 넣으면 될 수 있다 🔍).
- DOCX → MD 는 이미 xberg 파싱 결과(`content`)가 있다.

## 6. 도구 설계 방향

### 6.1 도구를 늘리지 않는다

`edit_document` 의 수정 하나에 **종류(`op`)** 를 붙여 넓힌다. 새 도구(`split_paragraph`, `insert_table_row` …)를 따로 만들지 않는다.

| 이유 | |
|---|---|
| 모델이 고를 도구가 늘지 않는다 | 도구가 많을수록 작은 모델(로컬 Ollama)이 엉뚱한 도구를 고른다 |
| 규칙을 그대로 쓴다 | "한 번 부르면 수정본 하나", 수정 목록을 한꺼번에 받는 구조 |
| 섞어 쓸 수 있다 | "p3 을 나누고, p7 을 지우고, 표에 행 추가" 를 한 번에, 수정본 하나로 |

### 6.2 수정 종류 (안)

초안. 묶음 1 에서 확정한 모양은 9.1절이다 (`split` 은 `replace` 의 `\n` 으로 합치고, 위치는 `position`·`target`, 표 행은 칸 안 문단 번호로 가리킨다).

```json
{ "op": "replace",          "old_text": "120억", "new_text": "135억", "paragraph": "p2" }
{ "op": "replace",          "old_text": "늘었다. 반면", "new_text": "늘었다.\n반면" }
{ "op": "merge",            "paragraph": "p5" }
{ "op": "insert_paragraph", "paragraph": "p12", "position": "after", "new_text": "결론적으로 …", "style": "본문" }
{ "op": "delete_paragraph", "paragraph": "p7" }
{ "op": "move_paragraph",   "paragraph": "p7", "position": "after", "target": "p2" }
{ "op": "insert_row",       "paragraph": "p23", "position": "after", "cells": ["부산", "18억"] }
{ "op": "delete_row",       "paragraph": "p27" }
{ "op": "comment",          "old_text": "135억", "paragraph": "p2", "new_text": "출처 확인 필요" }
```

- `op` 가 없으면 `replace` (지금 입력과 호환). 텍스트 형식은 `replace` 만.
- `comment` 는 묶음 2(B2).
- 종류가 늘수록 도구 스키마가 길어진다. 작은 모델이 따라오는지 fake 가 아닌 실제 모델로 확인해야 한다 🔍.

### 6.3 구조가 바뀌면 문단 번호가 밀린다

- 한 번 부를 때 받은 수정 목록의 `pN` 은 모두 **보기에서 본 번호(고치기 전 번호)** 로 해석한다.
- 적용은 문단 요소를 미리 붙잡아 두고(번호 → 요소) 순서대로 한다. 번호를 다시 세지 않는다. `old_text` 는 앞 수정을 적용한 글자에서 찾는다 (9.1절).
- 결과에 "문단 번호가 바뀌었으니 다시 보기로 확인하라" 를 붙인다. 다음 수정은 새 보기 기준.

### 9.1 묶음 1 상세 설계

#### 수정 종류 (`op`)

| `op` | 쓰는 필드 | 동작 |
|---|---|---|
| `replace` (기본) | `old_text`, `new_text`, `replace_all`, `paragraph` | 지금과 같다. `new_text` 의 `\n` 에서 문단을 나눈다 (A1). `old_text` 가 비고 `paragraph` 가 **빈 문단**(빈 표 칸 등)이면 그 문단에 `new_text` 를 채운다 (A3 칸 채우기) |
| `merge` | `paragraph` | `paragraph` 와 바로 다음 문단을 합친다. 경계 양쪽에 공백이 없으면 공백 하나를 넣는다 |
| `insert_paragraph` | `paragraph`, `position`, `new_text`, `style` | 기준 문단 앞(`before`)이나 뒤(`after`, 기본)에 새 문단을 넣는다. `\n` 이면 여러 문단 |
| `delete_paragraph` | `paragraph` | 문단을 지운다 |
| `move_paragraph` | `paragraph`, `position`, `target` | 문단을 `target` 문단 앞이나 뒤로 옮긴다 (서식 그대로) |
| `insert_row` | `paragraph`, `position`, `cells` | `paragraph` 가 든 표 행의 앞이나 뒤에 행을 넣고 `cells` 값을 칸마다 넣는다 |
| `delete_row` | `paragraph` | `paragraph` 가 든 표 행을 지운다 |

- 텍스트 형식(TXT·MD·CSV)은 `replace` 만 받는다. 다른 `op` 는 그 수정만 실패로 돌려준다.
- 표 열 넣기·지우기, 목록 수준 바꾸기, 문단 안 줄바꿈은 묶음 1 에서 빼고 뒤로 미룬다.

#### 문단 번호와 수정 순서

- 수정 안의 `pN`(`paragraph`, `target`)은 모두 **이번 호출을 시작할 때의 번호**(에이전트가 본 보기 번호)다. 앞 수정이 문단을 나누거나 지워도 뒤 수정의 `p7` 은 원래 p7 문단을 가리킨다.
  - 구현: 호출을 시작할 때 문단 요소마다 번호 표시(임시 속성)를 달고, 끝나면 지운다. 나눈 문단의 앞 조각이 원래 요소다.
  - 지워진 문단을 가리키면 그 수정은 실패.
- `old_text` 는 지금처럼 **앞 수정을 적용한 글자**에서 찾는다 (1단계와 같은 규칙).
- 결과에 구조가 바뀌었으면 "문단 번호가 바뀌었으니 새 수정본은 다시 보기로 확인하라" 를 붙인다.

#### 수정마다 따로 성공·실패 (C1)

- 수정 하나를 적용하기 전에 문서 상태를 저장해 두고, 그 수정이 실패하면 그 수정만 되돌린다 (`replace_all` 이 문단 여러 개를 고치다 실패해도 그 수정 전체가 취소).
- 결과: 성공한 수정의 바뀐 곳 요약 + 실패한 수정의 이유. 하나도 성공하지 못하면 지금처럼 오류("No changes were saved").
- CSV 검사와 "빈 문서가 된다" 검사는 모든 수정을 적용한 뒤 한 번 한다 (실패하면 전부 취소).

#### 문단 나누기 (A1)

- `\n\n` 처럼 이어진 줄바꿈은 하나로 본다. 나눈 결과에 **글자 없는 문단이 생기면 거절**한다 (빈 문단 넣기는 `insert_paragraph` 로도 하지 않는다).
- 새 조각은 원래 문단의 `w:pPr` 를 복사한다. `w:pPr` 안의 `w:sectPr`(구역 나누기)는 마지막 조각으로 옮긴다. 원래 요소의 속성(`w14:paraId` 등)은 복사하지 않는다.
- 나누는 자리의 run 은 둘로 쪼개고 `w:rPr` 를 복사한다. 나누는 자리 뒤의 형제 요소(run, 링크, 책갈피)는 새 조각으로 옮긴다.
- 거절: 나누는 자리가 링크·콘텐츠 컨트롤 등 묶음 안일 때, 복합 필드 안일 때.

#### 문단 넣기·지우기·옮기기 (A2, A4)

- 새 문단 서식: 기준 문단의 `w:pPr`(구역 나누기·변경 기록 빼고)와 첫 글자 run 의 `w:rPr`. 목록 문단이면 `w:numPr` 가 따라와 **번호가 이어진다** (A4).
  - 기준 문단이 제목이고 뒤에 넣으면, 다음 문단이 제목이 아닐 때 그 문단을 기준으로 삼는다 (제목 뒤에 넣는 글은 보통 본문).
  - `style` 을 주면 `w:pPr` 는 그 스타일만 두고 run 서식은 복사하지 않는다. 받는 값: `제목 1`~`제목 9`, `본문`(스타일 없음 = 기본), `문서 제목`, `부제목`, 또는 문서의 스타일 이름. 문서에 없는 스타일이면 실패.
- 지우기 거절: 구역 나누기(`w:sectPr`)를 가진 문단, 메모가 달린 문단, 복합 필드가 문단 밖으로 이어지는 문단, 변경 추적 문단. 책갈피는 짝(시작·끝)을 함께 지운다.
- 표 칸·본문의 마지막 문단이라 지우면 구조가 깨지면(칸에 문단이 없어지거나 표가 칸의 끝이 됨) 지우지 않고 **글자만 비운다**.
- 옮기기는 같은 부분(본문, 머리글 하나) 안에서만. 지우기와 같은 거절 조건.
- 보기에 목록 문단 표시 `(목록)`, `(목록 2수준)` 을 붙인다.

#### 표 행 넣기·지우기 (A3)

- 기준 행을 복사하고 칸마다 첫 문단의 `w:pPr`·첫 run 의 `w:rPr` 만 남겨 `cells` 값을 넣는다. 칸 수보다 값이 적으면 나머지 칸은 비운다. 많으면 실패.
  - 기준 행이 머리글 행(`w:tblHeader`)이고 아래 행이 있으면 아래 행을 복사한다. 복사본에서 `w:tblHeader`·`w:cnfStyle` 은 뺀다.
- 거절: 기준 행이나 넣는 자리 바로 아래 행에 세로 병합(`w:vMerge`)이 있을 때, 변경 추적 행, 표의 마지막 한 행 지우기, 메모가 달린 행 지우기.

#### 최신 수정본 확인 (C4)

- 고치려는 문서를 원본으로 만든 수정본(`source_document_id` 가 이 문서)이 같은 대화에 있으면 거절하고, 그 사슬의 마지막 수정본 document_id 를 알려 준다.
- 보기 도구는 막지 않는다 (예전 버전을 보는 것은 괜찮다).

- **`set_style`** (2026-11-24): 이미 있는 문단을 `제목 N`·`본문`·`문서 제목`·`부제목`·문서의 스타일 이름·`목록`/`목록 N수준` 으로 바꾼다.
  보기의 표시와 같은 말을 받는다. 제목·본문으로 바꾸면 목록 번호를 떼고, 목록이 아닌 문단을 목록으로 바꾸면 바로 앞·뒤 목록에 이어 붙인다 (새 목록 만들기는 안 됨).
- **보기의 `(빈 칸)`**: 빈 표 칸을 채우려면 그 문단 번호가 필요해서, 표 칸의 빈 문단만 보여준다.

### 11.1 목표와 범위

| B3 | 남이 남긴 변경 추적 기록 **보기**, 수락·거절 | ✅ 먼저 (B1 이 이 위에 선다) |
| B1 | 에이전트의 수정을 **변경 추적으로 남기기** | ✅ |

순서를 B3 → B1 → B2 로 하는 이유: 지금은 추적 기록이 있는 문단을 거절한다(결정 3). B1 로 추적을 남기면 다음 수정에서 우리 문단을 우리가 못 고치게 되므로, 추적 기록을 읽고 다루는 B3 이 먼저 있어야 한다.

### 11.2 지금 상태

- 펼치기(`_flatten`): `w:ins`·`w:moveTo` 글자는 보이고, `w:del`·`w:moveFrom` 은 숨긴다 (수락한 모습). 그런 문단은 `tracked=True`.
- 보기: `(변경 추적 기록 있음 · 고칠 수 없음)` 표시. 수정: 그 문단을 건드리는 모든 `op` 거절 (`_check_untracked`, 표 행도 같음).
- 메모: 읽지도 보여주지도 않는다. 메모가 달린 문단·행 지우기는 거절한다. 메모 범위 표시(`commentRangeStart` 등)는 펼칠 때 무시한다.
- 서식 복사(`_without_tracking`)는 `w:rPrChange`·`w:pPrChange` 등을 지운다.
- 🔍 파서(`xberg`)가 추적 기록이 있는 DOCX 의 `content` 에 지운 글자를 넣는지 모른다. 구현 1단계에서 확인한다.

### 11.3 B3 기존 변경 추적 기록 보기·수락·거절

#### 보기

추적 기록이 있는 문단만 표시를 바꾼다. 나머지 문단은 지금과 같다.

```
[p5] (변경 추적: 김민지) 매출은 {-120-}{+135+}억 원이다.
[p9] (변경 추적: 김민지 · 서식 바뀜) 결론
```

- 넣은 글자 `{+…+}`, 지운 글자 `{-…-}`. 옮긴 글자(`moveFrom`/`moveTo`)도 각각 `{-…-}`/`{+…+}` 로 보인다.
- 서식만 바뀐 것(`rPrChange`·`pPrChange`)은 글자로 보여줄 수 없어 라벨만 붙인다.
- 문단 기호의 추적(`w:pPr/w:rPr/w:ins|del`: 문단 나누기·합치기를 추적한 것)은 라벨 `문단 넣음·나눔 추적` · `문단 합침 추적` 으로.
- 범례에 표기 설명을 더한다. `{+`·`{-` 가 원래 글자에 있으면 헷갈리므로, 🔍 표기 대신 `⟦+…⟧` 같은 드문 기호를 쓸지 정한다.
- `old_text` 찾기는 지금처럼 **수락한 모습**(표기 없는 글자)에서 한다. 표기는 보기에만 있다. 🔍 모델이 표기째 복사하는 실수에는 힌트를 준다 (`[L12]` 힌트와 같은 방식).

#### 수락·거절

새 `op` 두 개: `accept_changes`, `reject_changes`.

| 인자 | 뜻 |
|---|---|
| `paragraph` (선택) | 이 문단만. 없으면 문서 전체 |
| `author` (선택, 🔍) | 이 사람이 남긴 것만 |

| 기록 | 수락 | 거절 |
|---|---|---|
| `w:ins` (글자) | 감싼 것만 벗긴다 | 안의 run 을 지운다 |
| `w:del` (글자) | 통째로 지운다 | 벗기고 `w:delText` → `w:t` |
| `w:moveTo` / `w:moveFrom` + 범위 표시 | ins/del 처럼 + 범위 표시 지움 | 반대 |
| `w:rPrChange` / `w:pPrChange` | 기록만 지운다 | 안의 옛 서식으로 되돌린다 |
| 문단 기호 `w:pPr/w:rPr/w:ins` | 기록만 지운다 | 다음 문단과 합친다 (문단 나누기 취소) |
| 문단 기호 `w:pPr/w:rPr/w:del` | 다음 문단과 합친다 | 기록만 지운다 |
| 표 구조(`w:trPr/w:ins·del`, `w:cellIns`·`cellDel`·`cellMerge`, `w:tblPrChange` 등), `w:sectPrChange`, `w:numberingChange` | ❌ 처음에는 거절 ("Word 에서 처리") | ❌ |

- 거절하는 기록이 범위 안에 하나라도 있으면 그 수정은 실패한다 (부분 적용하지 않는다, C1 수정 단위).
- 머리글·바닥글도 같은 규칙. 각주·미주·메모 본문 안의 추적은 건드리지 않는다.

#### 추적 기록이 있는 문단 고치기

결정 3(거절)을 좁힌다: **바꾸는 범위가 추적된 글자(`ins` 글자, 숨은 `del` 자리)에 닿지 않으면** 일반 글자처럼 고친다.
닿으면 지금처럼 거절하고 "먼저 수락·거절하라" 고 안내한다. 숨은 `del` 자리는 펼칠 때 길이 0 의 표시 글자로 기억해 경계를 판단한다.
구조 `op`(나누기·합치기·지우기·옮기기)는 추적 문단에서 계속 거절한다.

### 11.4 B1 변경 추적으로 고치기

#### 켜는 방법

`edit_document` 에 호출 단위 인자 `track_changes: bool | None` 을 더한다 (수정마다가 아니라 한 번에 하나의 수정본이므로).

| 값 | 동작 |
|---|---|
| `true` | 추적으로 남긴다. 사용자가 "변경 추적으로", "검토할 수 있게", "고친 곳 표시해서" 라고 했을 때 |
| `false` | 바로 고친다 (지금과 같음) |
| 없음 (기본) | 원본 `word/settings.xml` 에 `w:trackRevisions` 가 켜져 있으면 추적, 아니면 바로 고친다 (Copilot 방식) |

- 추적 모드에서 추적할 수 없는 수정은 **추적 없이 몰래 적용하지 않고 실패**시킨다 (사용자가 Word 에서 수락·거절할 수 있다고 믿기 때문이다).
- 원본의 `w:trackRevisions` 설정은 바꾸지 않는다.

#### 작성자·날짜·ID

- `w:author`: 🔍 설정값 하나 (`EDIT_AUTHOR`, 기본 `"AI 에이전트"`). 사용자 이름을 쓰면 사람이 고친 것과 구분이 안 된다.
- `w:date`: 호출 시각(UTC, 초 단위) 하나를 그 호출의 모든 기록에 쓴다. Word 는 같은 작성자·시각 기록을 묶어 보여준다.
- `w:id`: 문서 전체(본문·머리글·바닥글·각주)에서 쓰이는 변경 기록 id 의 최댓값 + 1 부터. 메모·책갈피 id 와 겹쳐도 되지만, 안전하게 모든 `w:id` 의 최댓값을 기준으로 한다.

#### 수정 종류별 추적 방법

| `op` | 추적 방법 | 1차 구현 |
|---|---|---|
| `replace` | 바꾸기 알고리즘의 diff 결과에서 지울 글자는 run 을 잘라 `w:del` + `w:delText`, 넣을 글자는 새 run 을 `w:ins` 로 감싼다. 서식은 지금 규칙 그대로 | ✅ |
| `replace` 의 `\n` (나누기) | 나뉜 앞 문단의 문단 기호에 `w:pPr/w:rPr/w:ins` | ✅ |
| `insert_paragraph` | 새 문단의 run 을 `w:ins`, 문단 기호에 `w:ins` | ✅ |
| `delete_paragraph` | run 을 모두 `w:del`, 문단 기호에 `w:del` (문단은 남는다) | ✅ |
| `merge` | 앞 문단 기호에 `w:del` (+ 넣은 공백은 `w:ins`) | 🔍 |
| `set_style` | `w:pPrChange` 에 옛 `w:pPr` 를 넣는다 | 🔍 |
| `insert_row` / `delete_row` | `w:trPr/w:ins` / `w:trPr/w:del` + 칸 글자 ins/del | 🔍 |
| `move_paragraph` | `moveFrom`/`moveTo` + 범위 표시 (이름·id 짝) | ❌ 처음에는 추적 모드에서 거절 |

- 같은 호출 안에서, 또는 다음 호출에서 **우리가 넣은 글자(`w:ins`, 작성자가 우리)** 를 다시 고치면 Word 처럼 그 `ins` 안을 바로 고친다 (지운 기록을 남기지 않는다). 다른 사람의 추적 글자는 11.3 규칙대로 거절.
- 결과 요약은 지금과 같고 끝에 `(tracked)` 를 붙인다. 보기에서는 11.3 표기로 우리 수정도 보인다.
- 수정본 파싱 `content` 는 수락한 모습이어야 한다 (🔍 파서 확인, 아니면 파싱 전에 수락한 사본을 만들어 넘긴다).

### 11.8 위험

- Word 는 잘못된 추적·메모 XML 에 "읽을 수 없는 내용" 오류를 낸다 (id 중복, `w:del` 안의 `w:t`, 범위 짝 누락). 기계 확인과 Word 확인이 꼭 필요하다.

"Word 로 만들어 줘", "이 양식으로 보고서 써 줘" 를 할 수 있게 한다. 지금은 `create_document` 가 TXT·MD·CSV 만 만들고, Word 를 원하면 MD 를 권한다.

| # | 기능 | 묶음 3 에 넣나 |
|---|---|---|
| D1 | Markdown 내용으로 **새 DOCX** 만들기 | ✅ |
| D2-a | 올린 DOCX 를 **양식으로** 새 DOCX 만들기 (머리글·바닥글·스타일·쪽 설정은 그대로, 본문만 새로) | ✅ |
| D2-b | 양식 안의 `{{이름}}` 같은 자리 채우기 | ✅ 새 기능 없음: `edit_document` 의 `replace`·`replace_all`·빈 칸 채우기로 이미 된다. 프롬프트로 안내만 |
| D3 | DOCX → PDF 내보내기 | ❌ (서버에 LibreOffice·한글 글꼴 필요, 이 맥의 headless LibreOffice 는 한글을 못 그린다) |

### 12.2 도구 모양

새 도구를 만들지 않고 `create_document` 를 넓힌다 (도구를 늘리지 않는다, 6.1).

```
create_document(filename="2024 영업 보고.docx", content="# 2024 영업 보고\n\n...", template_document_id=None)
```

- 확장자 `.docx` 면 `content` 를 **Markdown** 으로 읽어 Word 문서로 만든다. 모델이 가장 잘 쓰는 형식이고, 1단계 MD 만들기와 입력이 같다.
- `template_document_id` (선택, DOCX 만): 지금 대화의 DOCX 를 양식으로 쓴다 (D2-a).
- 결과·화면은 지금과 같다 (파일 칩 "새 문서"). 만든 뒤에는 `edit_document` 로 묶음 1·2 기능을 그대로 쓴다.
- 업로드 문서처럼 파싱해서(`processing` → `ready`) 다음 질문에서 `read_document` 가 읽게 한다. DOCX 수정본과 같이 `DOCUMENT_EDIT_PARSE_WAIT_SECONDS` 까지 기다린다.

### 12.3 만드는 방법

| 안 | 내용 | 판단 |
|---|---|---|
| A | 코드 안의 **기본 양식**(스타일·번호 정의·쪽 설정)에 본문 XML 만 lxml 로 만들어 넣는다 | ✅ 추천. 2단계 코드와 같은 방식, 양식(D2-a)과 같은 코드로 된다 |
| B | python-docx 를 만들기용으로만 쓴다 | 의존성이 늘고, 양식 문서에 쓰면 저장 때 다른 부분까지 다시 쓴다 (2단계 결정 5) |
| C | Pandoc 등 외부 변환기 | 이미지·운영 부담. 양식 재사용이 어렵다 |

- Markdown 읽기: **`markdown-it-py`** (MIT, 순수 Python, CommonMark + 표·취소선 켜기). 지금은 개발 의존성(rich)을 따라 4.2.0 이 들어와 있다. 실행 의존성으로 올리고 `<4.3.0` 제약은 그대로 둔다.
  직접 파서를 짜면 목록 안 목록, 표 안 `|`, 강조 짝 같은 경계 사례를 다시 만들어야 한다.
- 기본 양식은 **코드로 만든다** (바이너리 파일을 저장소에 두지 않는다). 부분: `[Content_Types].xml`, `_rels/.rels`, `word/document.xml`, `word/_rels/document.xml.rels`, `word/styles.xml`, `word/numbering.xml`, `word/settings.xml`, `docProps/core.xml`·`app.xml`.

### 12.4 Markdown → Word 대응

| Markdown | Word | 비고 |
|---|---|---|
| `#`~`######` | 스타일 `Heading1`~`Heading6` (이름 `heading 1`…) | 보기·`set_style` 이 이미 알아보는 이름 |
| 문단 | 기본 문단 (`Normal`) | 줄 하나 안의 줄바꿈(soft break)은 공백, 줄 끝 두 칸·`\` (hard break)는 `w:br` |
| `**굵게**`, `*기울임*`, `~~취소선~~`, `` `코드` `` | `w:b`, `w:i`, `w:strike`, 고정폭 글꼴 문자 스타일 | 겹쳐 쓰기 가능 |
| `[글](https://…)` | `w:hyperlink` + 외부 관계, 문자 스타일 `Hyperlink` | `http(s)`·`mailto` 만. 나머지는 글자만 |
| `-`/`*` 목록, `1.` 목록, 들여 쓴 목록 | `numbering.xml` 의 글머리표·번호 정의, `w:numPr`(수준 0~8) | 번호 목록은 목록마다 새 `w:num` 으로 1부터 다시 (시작 번호 `3.` 이면 3부터) |
| 표 (GFM) | `w:tbl`, 스타일 `TableGrid`(테두리), 머리글 행 `w:tblHeader` + 굵게, 열 정렬(`:---:`) | 너비는 쪽 너비를 열 수로 나눔 |
| `>` 인용 | 스타일 `Quote` (왼쪽 들여쓰기·테두리) | 인용 안 목록도 된다 |
| ```` ``` ```` 코드 블록 | 스타일 `Code` (고정폭, 회색 배경), 줄마다 `w:br` | 언어 표시는 무시 |
| `---` | 문단 아래 테두리(가로줄) | 🔍 쪽 나누기 표기를 따로 둘지 (12.8) |
| 이미지 `![](…)` | ❌ 글자(대체 텍스트)만 | 가져올 그림이 없다. 결과에 알린다 |
| HTML, 각주 | ❌ 글자 그대로 | |

- **한글 글꼴**: 기본 글꼴을 `w:rFonts` 의 `ascii`·`hAnsi`·`eastAsia`·`cs` 모두 "맑은 고딕" 으로 두고 언어 `w:lang w:eastAsia="ko-KR"`. 2단계 시험 문서에서 `eastAsia` 가 비어 다른 글꼴로 잡힌 경험이 있다. 맥에는 맑은 고딕이 없지만 Word·Quick Look 이 비슷한 글꼴로 바꿔 보여준다 🔍 (Quick Look 으로 확인).
- **쪽**: A4, 여백 사방 25.4mm (Word 기본). 🔍
- **문서 속성**: `docProps/core.xml` 의 만든 이 = `DOCUMENT_EDIT_AUTHOR`, 제목 = 첫 `#` 제목.

### 12.5 양식으로 만들기 (D2-a)

- 양식 DOCX 를 그대로 복사하고 **본문(`w:body`)의 내용만** 새로 만든다. 마지막 구역 설정(`w:sectPr`, 머리글·바닥글 연결·쪽 설정)은 남긴다.
- 스타일은 양식의 것을 이름으로 찾는다 (`heading 1`, `Quote`, `Table Grid` …). 양식에 없는 스타일은 기본 양식의 정의를 양식 `styles.xml` 에 더한다 (id 가 겹치면 새 id).
- 목록 번호 정의도 같다: 양식 `numbering.xml` 에 우리 정의를 더한다 (없으면 만들고 내용 형식·관계 등록, 묶음 2 메모 부분과 같은 방법).
- 본문에 있던 그림·표 등은 버린다. 그것들만 쓰던 관계(그림 파일)는 남아도 Word 는 문제없이 연다 🔍 (정리할지 12.8).
- 머리글·바닥글 안의 자리(`{{작성자}}`)는 만든 뒤 `edit_document` 로 채운다 (D2-b).

|---|---|
| 단위 | Markdown 요소마다 XML (스타일 id, `numPr` 수준, 번호 다시 시작, 표 머리글, 링크 관계, 공백 보존), 빈 내용·이미지 알림 |

### 12.7 위험

- 모델이 쓰는 Markdown 이 표준과 다를 수 있다 (표 앞 빈 줄 빠짐, `•` 글머리표). markdown-it 이 못 알아보면 글자 그대로 들어간다. → 🔍 `•`·`·` 로 시작하는 줄을 목록으로 볼지는 표본을 보고 정한다 (CLAUDE.md 규칙: 손 테스트로 동작을 바꾸기 전에 알린다).
- 양식마다 스타일 이름이 다르다 (한글 Word 의 "제목 1" 은 내부 이름이 `heading 1` 이라 대부분 맞지만, 사용자 정의 양식은 아닐 수 있다).
- 큰 문서: 내용 길이는 모델 출력 한계가 막는다. 파일 크기는 `DOCUMENT_MAX_BYTES`.

## 13. 묶음 4 설계 초안: 서식·화면 (2026-11-24)

상태: 13.8 결정은 사용자 지시("정할 것은 추천안으로, 직접 확인할 단계까지 진행")에 따라 추천안으로 진행한다.
근거는 6절(E1·C2·C3·F1·F2·B4)이고, 손 테스트 표본에서 나온 것이 아니다. E2(문단 스타일)는 묶음 1 의 `set_style` 로 끝났다.

### 13.1 목표와 범위

| # | 기능 | 쉽게 | 어디 |
|---|---|---|---|
| C2 | 보기에서 찾기 | 긴 문서에서 "환불" 이 든 문단만 번호와 함께 | 백엔드 |
| E1 | 글자 서식 넣고 빼기 | "이 금액 굵게", "빨간 글씨를 검정으로" | 백엔드 |
| C3 | 고쳐 쓰기에서 서식 지키기 | 문단을 번역해도 굵은 단어·링크가 남게 | 백엔드 |

백엔드(4-A: C2 → E1 → C3)를 먼저 하고 화면(4-B: F1 → B4 → F2)을 한다. 4-A 는 도구만 바꾸고, 4-B 는 도구를 바꾸지 않는다.

### 13.2 C2 보기에서 찾기

- `view_document_for_edit` 에 `query` 인자. 있으면 그 글자가 든 문단(DOCX)·줄(텍스트)만 번호와 함께 보여 준다.
- 맞추기: 대소문자 무시, 공백은 그대로. 추적 기록이 있는 문단은 수락한 모습(`text`) 에서 찾고 표기(`marked`)로 보여 준다.
- `start` 와 함께 쓰면 그 번호부터 찾는다 (많을 때 이어 보기). 머리말: `12 paragraphs match "환불" (showing p3-p88)`.
- 하나도 없으면 "없음" 과 전체 문단 수를 알린다. 문서를 처음부터 읽게 하지 않는다.
- 앞뒤 문단은 붙이지 않는다: 번호가 있으니 필요하면 `start` 로 그 근처를 본다 (토큰 절약).

### 13.3 E1 글자 서식

**도구 모양**: 새 `op: "format"` + 새 인자 `format`.

```json
{"op": "format", "old_text": "135억", "paragraph": "p12",
 "format": {"bold": true, "color": "red", "highlight": "none"}}
```

- `format` 의 필드: `bold`·`italic`·`underline`·`strike` (true 넣기 / false 빼기), `color` (`red` 같은 이름이나 `#C00000`, `auto` 는 기본색으로), `highlight` (Word 형광펜 이름 `yellow`·`green`… , `none` 은 빼기). 안 준 필드는 그대로.
- `old_text` 를 찾는 규칙은 `replace` 와 같다 (`paragraph`, `replace_all` 도 같음). `old_text` 가 비면 `paragraph` 문단 전체.
- 구현: 범위 경계에서 run 을 쪼개고(`_cut_run`) 조각마다 `w:rPr` 를 고친다. 자식 순서는 스키마 순서(`rStyle, rFonts, b, bCs, i, iCs, caps, …, strike, …, color, …, highlight, u, …`)를 지킨다.
- 굵게·기울임은 `b`+`bCs`, `i`+`iCs` 를 같이 (Word 와 같음).
- **빼기**: 직접 서식(`w:b`)을 지운다. 그래도 스타일(문자 스타일·문단 스타일·`basedOn` 사슬, 문서 기본값)이 굵게면 `w:b w:val="0"` 으로 끈다. 스타일이 굵게가 아니면 끄는 표시는 넣지 않는다 (XML 을 깨끗하게).
- 고칠 수 없는 글자: run 밖의 벽(수식 등)은 건너뛴다. 그림·필드 결과처럼 run 안의 것은 run 서식이 바뀌어도 문제없다. 링크 경계는 상관없다 (조각마다 따로 고친다).
- 이미 그 서식이면 바꾸지 않고 "바뀐 것 없음" 실패로 알린다 (헛 수정본 방지).
- **변경 추적**: 서식 변경은 `w:rPrChange`(옛 서식 사본)로 남긴다. 우리 `rPrChange` 가 이미 있으면 처음 옛 서식을 그대로 둔다. 남의 추적 글자는 지금처럼 거절. 그래서 `format` 은 추적 모드에서도 된다.
- **보기에 서식 보이기**: "빨간 글씨를 검정으로" 는 어느 글자가 빨간지 알아야 한다. 보기는 `old_text` 를 복사하는 곳이라 글자 안에 표시를 넣지 않고, `view_document_for_edit` 에 `formatting: true` 를 주면 문단 아래에 `    (서식: 굵게 '135억' · 빨강 '주의' · 형광펜 노랑 '마감')` 줄을 붙인다. 기본은 끔 (굵은 글자가 많은 문서에서 토큰이 늘어난다). 직접 서식만 보여 준다 (스타일로 굵은 제목 등은 이미 `(제목 1)` 로 보인다).

### 13.4 C3 고쳐 쓰기에서 서식 지키기

- 지금: 원래 글자와 새 글자가 절반 넘게 다르면(결정 8) 범위를 통째로 바꾸고, 새 글자 전체가 첫 글자의 서식을 따른다. 그 안의 굵은 단어·링크·위첨자가 사라진다.
- 바꾸는 방법: 통째로 바꾸기 전에 **서식이 다른 조각**(첫 글자와 run 서식이 다르거나 링크 안인 조각)을 찾고, 그 조각 글자가 새 글자에 **정확히 한 번** 나오면 그 자리는 "같음" 으로 둔다. 순서가 뒤집히는 조각은 버린다 (앞에서부터 고른다). 나머지만 통째로 바꾼다.
  - 예: `**135억** 원의 매출` → `매출은 135억 원` 이면 `135억` 은 굵게 남고 나머지는 첫 서식.
  - 조각 글자가 공백을 빼고 2글자 미만이면 쓰지 않는다 (`1`, `의` 같은 우연한 일치 방지).
- 변경 추적 경로(`_tracked_replace`)도 같은 비교 함수(`_diff_ops`)를 쓰므로 함께 좋아진다.
- 하지 않는 것: 번역처럼 조각 글자가 새 글에 없으면 서식을 옮길 방법이 없다. 그때는 결과에 "서식 있던 조각 N개가 새 글에 없어 첫 서식을 따름" 을 알리고, 에이전트가 `format` 으로 다시 입힐 수 있게 한다.

### 13.5 F1 미리보기

- 수정본·새 문서 칩을 누르면 오른쪽 패널(지금 프로젝트 문서 보기와 같은 자리)이 열린다. 받기는 패널 위 버튼과 칩의 받기 아이콘으로.
- DOCX: 브라우저에서 `docx-preview`(Apache-2.0, 서버 부담·한글 글꼴 문제 없음)로 원본 파일을 그린다. 파일은 지금 받기 API(쿠키 인증)를 `fetch` 해서 쓴다.
- TXT·MD·CSV: 글자를 받아 TXT 는 그대로, MD 는 Markdown 으로, CSV 는 표로.
- 패널 탭: `미리보기` · `바뀐 곳` (직전 버전이 있을 때) · `버전`.

### 13.6 B4 비교

- API `GET /api/documents/{id}/changes`: 직전 버전(`source_document_id`)과 이 문서를 비교한다.
  - DOCX: 두 파일을 `DocxDocument` 로 열어 문단 글자(수락한 모습)를 문단 단위로 비교(`SequenceMatcher`), 바뀐 문단 안은 낱말 단위로.
  - 텍스트: 줄 단위로 같은 방식.
  - 결과: 블록 목록 `{kind: same|changed|added|removed, label: "p12", parts: [{op: equal|insert|delete, text}]}`. 같은 문단이 길게 이어지면 앞뒤 1개만 남기고 접는다 (`skipped: 40`).
- 화면: 지운 글자는 빨강 취소선, 넣은 글자는 초록 밑줄. 서식만 바뀐 곳은 글자가 같아서 비교에 안 나온다 → 결과의 변경 요약(도구 결과)과 미리보기로 본다. 이건 화면 안내 문구로 알린다.
- 파서 결과(`content`)가 아니라 원본 파일에서 비교한다: 수정본 파싱이 끝나기 전에도 되고, 에이전트가 본 글자와 같다.

### 13.7 F2 버전 목록·되돌리기

- API `GET /api/documents/{id}/versions`: 같은 대화에서 `source_document_id` 로 이어진 사슬(맨 처음 원본부터 가장 새 수정본까지)을 돌려준다. 갈래가 있으면 가장 새 것을 따른다 (`latest_revision` 과 같은 규칙).
- API `POST /api/documents/{id}/restore`: 그 버전의 파일을 그대로 복사해 **가장 새 수정본 뒤에** 새 수정본을 만든다 (`revision` = 최신 + 1, `source_document_id` = 최신, 이름 `… (수정 N).docx`). 이전 버전은 지우지 않는다. 가장 새 버전이면 409.
  - 에이전트는 다음 수정 때 예전 id 를 쓰면 C4 규칙("더 새 버전이 있음")으로 새 id 를 안내받는다. 되돌린 사실을 대화에 따로 넣지는 않는다.
- 화면: `버전` 탭에 목록(버전, 만든 쪽 사용자/에이전트, 시각, 크기), 각 행에 받기·미리보기, 최신이 아니면 "이 버전으로 되돌리기".

| A5 | 제목 단위(섹션) 옮기기·지우기·넣기 | "3장을 2장 앞으로", "부록 빼 줘" | 문단 하나씩만 |
| A6 | 문단 안 줄바꿈 | 주소·서명을 한 문단 안에서 줄만 바꾸기 | `\n` 은 늘 문단 나누기 |
| A7 | 글 ↔ 표 바꾸기 | "이 목록을 표로 정리해 줘" | 안 됨 |

하지 않는 것: 변경 추적 모드에서 이번 묶음의 새 수정(묶음 6), 머리글·바닥글·글상자 안 표 구조(묶음 7), 그림(묶음 7).

### 14.2 도구 모양

6.1절 원칙대로 새 도구 없이 `edit_document` 의 `op` 를 늘린다.

| 바꾸는 것 | 내용 | 기능 |
|---|---|---|
| 새 `op: "insert_markdown"` | `paragraph` 앞이나 뒤에 Markdown 으로 쓴 내용(제목·문단·목록·표)을 넣는다 | 표 만들기, 새 목록, 섹션 넣기, A7 |
| 새 `op: "insert_column"` | `paragraph` 가 든 칸의 열 앞이나 뒤에 열을 넣고 `cells` 를 위에서 아래로 채운다 | A3 |
| 새 `op: "delete_column"` | `paragraph` 가 든 칸의 열을 지운다 | A3 |
| 새 `op: "delete_table"` | `paragraph` 가 든 표를 통째로 지운다 | 표 지우기, A7 |
| 새 인자 `whole_section` | `delete_paragraph`·`move_paragraph` 에서 `true` 면 제목 문단부터 그 섹션 끝까지 | A5 |
| 글자 `⏎` | 보기에서 문단 안 줄바꿈을 `⏎` 로 보이고, `old_text`·`new_text`·`cells` 의 `⏎` 를 줄바꿈으로 받는다 | A6 |
| `set_style` 값 | `번호 목록`·`글머리표 목록` (+ `N수준`) | A4 |
| `insert_row` | 세로 병합 표에서도 된다 | A3 |

- `op` 가 12개 → 16개. 작은 모델이 따라오는지는 손 테스트에서 본다 (6.2절의 걱정 그대로).
- 예시

```json
{"op": "insert_markdown", "paragraph": "p12", "position": "after",
 "new_text": "## 4. 일정\n\n| 단계 | 기간 |\n|---|---|\n| 설계 | 2주 |\n| 구현 | 4주 |"}
{"op": "insert_column", "paragraph": "p31", "position": "after", "cells": ["비고", "", "확인 필요"]}
{"op": "delete_column", "paragraph": "p33"}
{"op": "delete_table", "paragraph": "p40"}
{"op": "move_paragraph", "paragraph": "p50", "target": "p20", "position": "before", "whole_section": true}
{"op": "replace", "old_text": "서울시 중구 세종대로 110", "new_text": "서울시 중구⏎세종대로 110"}
{"op": "set_style", "paragraph": "p7", "style": "번호 목록"}
```

### 14.3 A6 문단 안 줄바꿈

- 문제: 지금 보기는 문단 안 줄바꿈(`w:br`)을 날것의 줄바꿈으로 보여서 `[pN]` 줄 모양이 깨지고, `new_text` 의 `\n` 은 문단 나누기라서 줄바꿈을 넣을 방법이 없다.
- 표기: 보기에서 `w:br`(글자 줄바꿈)·`w:cr` 을 `⏎` 로 보인다. 수정의 `old_text`·`new_text`·`cells` 에 `⏎` 가 있으면 `w:br` 로 넣고 찾는다. `\n` 은 지금처럼 문단 나누기.
  - `old_text` 에 날것의 `\n` 으로 줄바꿈을 찾던 지금 동작은 그대로 둔다 (호환).
  - 쪽 나누기(`w:br w:type="page"`)·단 나누기는 지금처럼 고칠 수 없는 자리(`￼`)다.
- 문서에 원래 `⏎` 글자가 있으면 구분이 안 된다 → 그 문단에서 `⏎` 를 쓰는 수정은 거절한다 (드묾).
- 변경 추적: 바꾸기 경로가 그대로 `w:br` 토큰을 `w:ins` run 에 넣으므로 추적 모드에서도 된다.
- 비교 화면(`compare.py`)·서식 보기도 `⏎` 로 보인다 (`Paragraph.text` 는 그대로 두고 보여줄 때만 바꾼다).

### 14.4 A3 세로 병합 표의 행

- 세로 병합: 위 칸 `w:vMerge w:val="restart"`, 아래로 이어지는 칸 `w:vMerge`(값 없음 = continue). 글자는 시작 칸에만 있다.
- **넣기**: 넣는 자리가 병합 구역 **가운데**(위 행과 아래 행이 같은 구역)면 새 행의 그 열 칸을 `continue` 로 만들어 구역을 늘린다 (Word 의 행 삽입과 같음). 구역의 위·아래 경계면 병합 없는 새 칸. 그 칸에 준 `cells` 값은 무시하고 결과에 알린다.
- **지우기**:
  - 지우는 행의 칸이 `restart` 이고 아래 행이 `continue` 면, 아래 칸을 `restart` 로 바꾸고 지우는 칸의 글자(문단)를 옮긴다 (병합 칸의 내용이 사라지지 않게).
  - 구역이 한 행만 남으면 `vMerge` 를 뗀다.
- **보기**: `continue` 칸은 빈 문단이라 지금 `(빈 칸)` 으로 보여 에이전트가 채우려 한다 → `(위 칸과 병합)` 으로 보이고, 그 칸을 채우는 수정은 거절한다 (시작 칸의 번호를 알려 준다).
- 가로 병합(`gridSpan`)이 있는 행도 넣기·지우기는 지금처럼 기준 행을 복사하므로 된다.

### 14.5 A3 표 열 넣기·지우기

- **열 위치**: 행마다 `w:gridBefore` + 칸들의 `w:gridSpan` 을 더해 칸 → 격자 열 범위를 계산한다. 보기의 `n열` 은 칸 순서라서 가로 병합이 있으면 행마다 다를 수 있다 → 열은 늘 **`paragraph` 가 든 칸의 격자 열**로 정하고, 결과에 그 열의 첫 행 글자를 적는다 (`inserted a column after '금액' in 표1`).
- **넣기**
  - 새 경계가 가로 병합 칸 **가운데**를 지나면 그 칸의 `gridSpan` 을 1 늘린다 (병합된 제목 행이 그대로 넓어짐).
  - 아니면 같은 행의 기준 칸을 `_blank_cell` 로 복사한다 (칸 서식·첫 문단 서식·첫 글자 서식, `vMerge`·`gridSpan` 은 뺌).
  - `cells` 는 위에서 아래로 행마다 하나 (머리글 행 포함). 적으면 나머지는 빈 칸, 많으면 실패. `gridSpan` 을 늘린 행의 값은 무시하고 알린다.
- **지우기**: 그 격자 열만 덮는 칸은 지우고, 걸쳐 있는 가로 병합 칸은 `gridSpan` 을 1 줄인다. 거절: 표의 마지막 열, 메모가 있는 칸, 칸 밖으로 이어지는 필드.
- **너비**: 표 전체 너비를 지킨다.
  - 넣기: 새 열은 기준 열과 같은 몫을 받고 나머지 열을 비율대로 줄인다 (`gridCol` 과 `dxa` 로 적힌 `tcW` 를 함께 고침).
  - 지우기: 지운 너비를 남은 열에 비율대로 나눠 준다.
  - `tcW` 가 `pct`·`auto` 면 `gridCol` 만 고친다.
- 거절: `gridBefore`·`gridAfter` 가 새 경계에 걸린 행, 추적 기록이 있는 표, 중첩 표 안에서 바깥 표 열 (가장 안쪽 표만 다룬다).

### 14.6 표 만들기·지우기, A4 새 목록, A5 섹션 넣기, A7: `insert_markdown`

하나의 수정으로 네 가지를 해결한다. 묶음 3 의 Markdown → Word 변환기(`docx_create._Builder`)를 기존 문서에 쓴다.

- **넣는 것**: 제목(`#`~`######`), 문단(굵게·기울임·취소선·코드·링크), 목록(중첩), 표, 인용, 코드 블록, 가로줄. 그림·HTML 은 묶음 3 과 같이 글자로 넣고 알린다.
- **문서와 어울리게**
  - 제목·인용·코드·표 스타일: 문서에 같은 이름의 스타일이 있으면 그것을 쓰고, 없으면 기본 정의를 더한다 (묶음 3 의 `_Styles`).
  - 스타일 없는 문단: `insert_paragraph` 와 같은 규칙으로 기준 본문 문단의 문단 서식·첫 글자 서식을 따른다 (문서의 본문이 직접 서식으로 크기·글꼴을 정해도 같게 보임).
  - 표 너비: 묶음 3 은 A4 본문 너비로 고정했다 → 넣는 자리의 구역(`w:sectPr` 의 `pgSz` − 좌우 `pgMar`) 너비로 나눈다.
  - 목록: 문서 본문에 같은 종류(번호·글머리표) 목록 정의가 있으면 그 `abstractNum` 에 새 `num`(번호 목록은 1부터 다시)을 만들어 모양을 맞춘다. 없으면 기본 정의를 더한다. `numbering.xml` 이 없는 문서면 만들고 관계·내용 형식에 등록한다.
  - 링크: 본문 부분의 관계에 외부 링크를 더한다.
- **위치**: 본문 바로 아래 문단의 앞·뒤만 (표 칸·머리글·바닥글·콘텐츠 컨트롤 안은 거절. 표 칸에는 `insert_paragraph`).
- **섹션 넣기**(A5): `## 새 장\n\n본문…` 을 넣으면 된다.
- **새 목록**(A4): `1. 첫째\n2. 둘째` 를 넣으면 된다. 이미 있는 문단을 목록으로 바꾸는 것은 14.7.
- **글 ↔ 표**(A7): 새 수정 없이 한 호출에서 `insert_markdown`(표) + 원래 문단 `delete_paragraph`, 또는 `insert_markdown`(문단·목록) + `delete_table`. 원래 글자의 서식(굵게 등)은 Markdown 으로 다시 쓴 만큼만 남는다. 시스템 프롬프트에 이 조합을 적는다.
- `delete_table`: 가장 안쪽 표를 지운다. 거절: 메모, 표 밖으로 이어지는 필드, 추적 기록. 지우면 구조가 깨지는 자리(표 칸의 유일한 내용 등)는 빈 문단을 남긴다 (`_keeps_structure`). 책갈피 짝을 정리한다.
- 결과: `inserted 1 heading, 2 paragraphs, 1 table (3 rows) after p12` 처럼 무엇을 넣었는지 센다. 문단 번호가 밀린다는 안내는 지금과 같다.

### 14.7 A4 이미 있는 문단을 새 목록으로

- `set_style` 에 `번호 목록`·`글머리표 목록`(+ `2수준` 등)을 더한다.
  - 바로 앞·뒤가 같은 종류 목록이면 이어 붙인다. 아니면 새 목록을 시작한다 (정의는 14.6 과 같은 규칙).
  - 한 호출에서 이어진 문단 여럿에 차례로 주면 첫 문단이 새 목록을 만들고 나머지는 앞 문단에 이어 붙는다.
- 지금의 `목록`(종류를 말하지 않음)은 그대로 이어 붙이기만 하고, 이어 붙일 목록이 없으면 "`번호 목록`이나 `글머리표 목록`으로" 를 안내한다.
- 보기 표시: 지금 `(목록)`·`(목록 2수준)` → `(번호 목록)`·`(글머리표 목록 2수준)` 처럼 종류를 보인다 (어느 값을 줄지 알 수 있게). 종류를 알 수 없는 정의는 `(목록)`.

### 14.8 A5 섹션 옮기기·지우기

- **섹션**: 본문 바로 아래의 제목 문단(스타일 `heading N` 이나 `w:outlineLvl`, 보기의 `(제목 N)`)부터, 같거나 높은 수준의 다음 제목 전까지의 블록(문단·표·콘텐츠 컨트롤). 본문 끝의 `w:sectPr` 는 넣지 않는다.
- `whole_section: true` 는 `delete_paragraph`·`move_paragraph` 에서 `paragraph` 가 제목일 때만. 제목이 아니면 실패 ("`(제목 N)` 문단을 주라").
- **옮기기**의 `target`: `before` 는 그 문단 앞. `after` 는 `target` 이 제목이면 **그 섹션 끝 뒤**("2장 뒤로" 가 2장 제목 바로 뒤가 아니라 2장 전체 뒤), 아니면 그 문단 뒤. 자기 섹션 안으로 옮기면 실패.
- **거절**: 범위 안에 구역 나누기(`w:pPr/w:sectPr`), 추적 기록, 범위 밖으로 이어지는 필드, 범위를 걸치는 메모(시작·끝 중 하나만 안). 지우기는 메모가 있으면 거절 (문단 지우기와 같음). 책갈피 짝 정리.
- 결과: `moved section '2. 시장 현황' (p12-p30: 18 paragraphs, 1 table) before p8`.
- 제목 스타일 없이 굵은 큰 글씨로만 만든 "제목" 은 섹션으로 알 수 없다 → 실패 안내로 `set_style` 로 제목을 먼저 정하거나 문단을 하나씩 옮기게 한다.

### 14.10 검증

- 단위 테스트
  - 줄바꿈: 보기 `⏎`, 넣기·찾기, 표 칸 값, 추적 모드, 원래 `⏎` 글자 거절.
  - 병합 행: 구역 가운데·경계에 넣기, 시작 행 지우기(글자 옮김), 한 행만 남으면 병합 떼기, 보기 표시, 채우기 거절.
  - 열: 격자 계산(`gridBefore`·`gridSpan`), 넣기·지우기, 너비 합 유지, `gridSpan` 조정, 마지막 열 거절.
  - `insert_markdown`: 제목·목록·표·링크, 문서 스타일 재사용·없을 때 더하기, `numbering.xml` 없는 문서, 표 너비, 본문 아닌 자리 거절.
  - `delete_table`, `set_style` 새 목록, 섹션 범위·옮기기(`after` 섹션 끝)·지우기·거절.
- 실제 파일: `assert_valid`, Quick Look(글자·표 모양), LibreOffice(열 너비·병합·목록 번호. Quick Look 은 열 너비를 정확히 그리지 않는다).
- E2E(fake 모델): 한 호출에서 섹션 옮기기 + 표 넣기 + 열 넣기 + 줄바꿈.
- 사용자: Word 로 열기, 실제 모델이 늘어난 `op` 를 고르는지.

### 14.11 위험

- 복잡한 표(`gridBefore`/`gridAfter`, 중첩 표, 너비가 `pct`)에서 열 계산이 틀리면 Word 가 표를 고치겠다고 할 수 있다 → 걸리는 모양은 거절하고, 시험 문서 여러 개를 LibreOffice 로 연다.
- `insert_markdown` 의 모양이 주변과 다를 수 있다 (특히 글머리표 기호, 표 테두리) → 문서 정의를 먼저 쓰는 규칙(결정 10)과 손 확인.
- `op` 와 설명이 늘어 작은 모델이 헷갈릴 수 있다 → 도구 설명은 짧게, 예시는 시스템 프롬프트에.
- `⏎` 를 모델이 `\n` 과 섞어 쓸 수 있다 → 결과 요약에 "문단을 나눴음"·"줄을 바꿨음" 을 구분해 적는다.


### 15.3 B1 구조 수정을 추적으로

| `op` | 추적 방법 | Word 와 같나 |
|---|---|---|
| `merge` | 앞 문단의 문단 기호에 `w:del`, 사이에 넣은 공백은 `w:ins`. 수락하면 묶음 2 의 `_join_next` 가 합친다 | ✅ |
| `set_style` (제목·목록·스타일) | `w:pPr` 끝에 `w:pPrChange` (안에 옛 `w:pPr`, `w:rPr`·`w:sectPr`·`w:pPrChange` 빼고). 새 목록 정의(`numbering.xml`)·새 스타일은 추적하지 않는다 (Word 도 정의는 추적하지 않음) | ✅ |
| `insert_row` | `w:trPr` 에 `w:ins` + 칸 글자 run `w:ins`, 칸 문단 기호 `w:ins`. 세로 병합 구역을 늘린 칸도 같다 | ✅ |
| `delete_row` | `w:trPr` 에 `w:del` + 칸 글자 `w:del`. 행은 문서에 남는다. **세로 병합 시작 칸 글자를 아래로 옮기는 정리(14.4)는 하지 않는다** (수락할 때 Word 가 한다 🔍) | ✅ |
| `insert_markdown` | 새 문단은 `insert_paragraph` 와 같이 (글자 + 문단 기호 `w:ins`), 새 표는 모든 행 `w:trPr/w:ins` + 글자 `w:ins` | ✅ |
| `delete_table` | 모든 행 `w:trPr/w:del` + 글자 `w:del` | ✅ |
| `delete_paragraph` + `whole_section` | 범위 안 문단은 `delete_paragraph` 추적과 같이, 표는 `delete_table` 추적과 같이. 메모는 지운 글자에 붙은 채 남는다 (15.6) | ✅ |
| `move_paragraph` (+ `whole_section`) | 🔍 결정 4. 추천: **옛 자리 지움 + 새 자리 넣음** (내용을 복사해 새 자리에 `ins`, 옛 자리는 `del`) | 표시가 "옮김" 이 아니라 "지움·넣음" |
| `insert_column` / `delete_column` | ❌ 계속 실패. Word 는 열 넣기·지우기를 행 기록으로 남기지 못하고, 칸 기록(`cellIns`)은 Word·LibreOffice 지원이 불안정하다 🔍 | — |

- 우리가 넣은 것을 다시 지우면 기록 없이 없앤다 (묶음 2 규칙을 넓힘): 우리 `w:trPr/w:ins` 행을 `delete_row` 하면 행을 그냥 지우고, 우리가 넣은 문단(문단 기호가 우리 `ins`)을 지우면 문단을 그냥 지운다.
- 추적으로 지운 행·문단(`w:del` 기록이 있는 것)을 다시 고치거나 옮기는 수정은 실패 ("먼저 수락·거절").
- 옮기기를 지움 + 넣음으로 하면 옛 자리 문단이 남아 문단이 늘어난다. 결과에 "문단 번호가 밀림" 안내는 지금과 같고, 보기에서 옛 자리는 `{-…-}` 로 보인다.
- 요소 순서를 지킨다: `w:trPr` 안에서 `w:ins`·`w:del` 은 다른 행 속성 뒤, `w:trPrChange` 앞. `w:pPrChange` 는 `w:pPr` 의 마지막. 어기면 Word 가 "읽을 수 없는 내용" 을 낸다.

### 15.4 B3 구조 기록 수락·거절

| 기록 | 수락 | 거절 |
|---|---|---|
| `w:trPr/w:ins` (행 넣음) | 기록만 지운다 | 행을 지운다 (14.4 의 병합 정리 `_unmerge_row` 를 거친다) |
| `w:trPr/w:del` (행 지움) | 행을 지운다 (병합 정리) | 기록만 지운다 |
| `w:tblPrChange`·`w:tblGridChange`·`w:trPrChange`·`w:tcPrChange`·`w:tblPrExChange`·`w:sectPrChange` | 기록만 지운다 | 지금 속성을 기록 안의 옛 속성으로 바꾼다 (묶음 2 의 `pPrChange` 거절과 같은 방식) |
| `w:numberingChange` (옛 Word 의 번호 기록) | 기록만 지운다 | ❌ 실패 (옛 번호 글자만 들어 있어 되돌릴 수 없다) |
| `w:cellIns`·`w:cellDel`·`w:cellMerge`, `w:customXml…RangeStart` | ❌ 실패 (지금과 같음) | ❌ |

- 표의 모든 행이 지워지면 표를 통째로 지운다. 지우면 구조가 깨지는 자리(칸의 유일한 내용 등)는 빈 문단을 남긴다 (`_keeps_structure`).
- 범위: `paragraph` 를 주면 그 문단과, 그 문단이 든 **행**의 행 기록·그 표의 표 기록, 그 문단이 끝인 구역의 구역 기록. 없으면 문서 전체 (지금과 같음).
- 실패하는 기록이 범위에 하나라도 있으면 그 수정 전체가 실패한다 (C1, 지금과 같음). 작성자를 주면 **그 사람의 기록만** 보고 판단한다.

#### 작성자별 (`author`)

- 모든 기록의 `w:author` 를 비교한다 (앞뒤 공백 무시, 대소문자 구분). 문단 기호 기록·서식 기록·구조 기록도 같다.
- 그 사람의 기록이 범위에 없으면 실패하고, 문서에 있는 작성자 목록을 알려 준다 (보기의 `(변경 추적: …)` 와 같은 이름).
- 다른 사람의 기록이 섞인 자리: 넣은 글자 안에 다른 사람이 지운 글자처럼 겹친 기록은 바깥 기록을 수락할 때 안쪽 기록을 그대로 둔다. 바깥을 거절하면(넣은 글자 지움) 안쪽 기록도 함께 사라진다 — Word 와 같다.
- 보기의 `(변경 추적: 김민지, AI 에이전트)` 이름을 그대로 쓰면 된다고 도구 설명에 적는다.

### 15.5 보기에 더할 것

```
[p31] (표1 3행 1열 · 행 넣음 추적: 김민지) 부산
[p40] (표2 · 표 서식 바뀜 추적) 항목
[p12] 2024년 매출은 120억 원이다.
      (메모 c3 · 김민지: "근거 자료가 필요합니다" → '120억 원')
      (  ↳ 답글 c4 · AI 에이전트: "출처를 각주로 달았습니다.")
      (메모 c5 · 박지훈: "표현 다듬기" → '매출' · 해결됨)
```

- 행 기록은 그 행 칸 문단의 위치 표시에, 표·구역 서식 기록은 그 표 첫 칸·구역 끝 문단에 라벨로 붙인다.
- 답글은 부모 메모 줄 바로 아래에 들여 쓴다. 해결된 메모는 `· 해결됨`. 범례에 설명을 더한다.
- 답글·해결 정보는 `word/commentsExtended.xml` 에 있다 (`w15:commentEx` 의 `w15:paraId`, `w15:paraIdParent`, `w15:done`). 메모의 마지막 문단 `w14:paraId` 로 메모와 짝짓는다. 이 부분이 없는 문서(LibreOffice·옛 Word)는 지금처럼 보인다.

### 15.6 B2 메모 답글·해결·지우기

#### 답글 (`comment` + `comment: "c3"`)

- `comments.xml` 에 새 `w:comment` 를 더한다. 작성자·날짜·`w:initials` 는 묶음 2 와 같다. 새 메모 문단에 `w14:paraId`(8자리 16진수, `0x80000000` 미만, 문서 안에서 유일)를 붙인다.
- 부모 메모의 마지막 문단에 `w14:paraId` 가 없으면 붙인다 (부모 메모 XML 이 바뀌는 유일한 곳).
- `commentsExtended.xml` 에 `<w15:commentEx w15:paraId="새" w15:paraIdParent="부모" w15:done="0"/>` 를 더한다. 부분이 없으면 묶음 5 의 `_create_part` 로 만들고 내용 형식·관계(Office 2011 관계 형식)를 등록한다. 부모 메모의 항목이 없으면 같이 만든다.
- 본문: Word 처럼 답글도 부모와 같은 자리에 범위 표시·표시 run 을 둔다 (부모 범위 시작 뒤·끝 뒤에 넣는다). 표시가 없으면 Word 가 답글을 따로 떨어진 메모로 보인다 🔍.
- 답글의 답글은 받지 않는다: `c4` 가 답글이면 부모 `c3` 의 답글로 단다 (Word 의 스레드는 한 단계).
- `commentsIds.xml`(`w16cid:durableId`)·`commentsExtensible.xml` 은 만들지 않는다. 있는 문서면 새 메모 항목을 더한다 🔍 (없어도 Word 가 여는지 1단계에서 확인).

#### 해결 (`resolve_comment`)

- `commentsExtended.xml` 의 그 메모 항목에 `w15:done="1"` (부분·항목이 없으면 만든다). 답글에 주면 부모 스레드를 해결한다.
- `new_text` 가 있으면 먼저 답글을 달고 해결한다 ("이렇게 고쳤습니다" 후 해결).
- 이미 해결된 메모면 실패하지 않고 결과에 알린다. 해결 취소는 하지 않는다 (요청이 드묾. 필요하면 나중에 `resolved: false`).
- `commentsExtended` 를 읽지 않는 프로그램(LibreOffice 옛 버전)에서는 해결 표시가 안 보일 수 있다 🔍.

#### 지우기 (`delete_comment`)

- 그 메모와 모든 답글의 `w:comment`, 본문의 범위 표시·표시 run, `commentsExtended`·`commentsIds`·`commentsExtensible` 의 항목을 지운다. 표시 run 이 표시 하나만 가진 run 이면 run 째 지운다.
- 답글을 주면 그 답글만 지운다.
- 메모가 모두 없어져도 `comments.xml` 은 빈 채로 남긴다 (관계 정리를 피한다).
- 추적 모드여도 기록 없이 지운다 (Word 도 메모 지우기는 추적하지 않는다).

#### 메모가 달린 문단 지우기

- 바로 지우기: 지금처럼 실패하되, 안내를 "같은 호출에서 `delete_comment` 를 먼저" 로 바꾼다. 메모를 말없이 잃지 않는다. 🔍 결정 7
- 추적으로 지우기: 허용한다. 메모는 지운 글자에 붙은 채 남는다 (Word 와 같음). 지금 `_tracked_delete` 의 메모 거절을 푼다.

### 15.7 도구와 프롬프트

- `DocumentEdit`: `op` 에 `resolve_comment`·`delete_comment`, 필드 `author`·`comment`. `comment` 값은 `c3`·`3` 둘 다 받는다.
- 결과: `accepted 4 tracked changes by 김민지 in the document`, `replied to comment c3`, `resolved comment c3 (and 1 reply)`.
- 시스템 프롬프트: 추적 모드에서 할 수 없는 것을 "열 넣기·지우기" 로 줄이고, 메모대로 고친 뒤 해결 표시는 사용자가 원할 때만 한다고 적는다 (멋대로 해결하면 검토자가 확인할 기회를 잃는다).

### 15.10 위험

- Word 는 추적·메모 XML 순서와 짝에 엄격하다. 행 기록 위치, `pPrChange` 위치, 답글의 `paraId` 짝이 틀리면 파일을 고치겠다고 한다 → `assert_valid` 에 규칙을 넣고, 사용자가 Word 로 한 번 연다. LibreOffice 는 잘못된 파일도 연다 (11.11 1단계).
- 추적으로 지운 행·문단·옮긴 옛 자리가 문서에 남아 보기가 길어지고 문단 번호가 복잡해진다 → 보기 표기·결과 안내로 설명한다.
- 작성자 필터로 일부만 수락하면 서로 겹친 기록이 남는다 → 15.4 의 겹침 규칙을 테스트로 고정한다.
- 시험 문서: 답글·해결·행 기록을 Word 가 만든 실제 파일이 없다. LibreOffice 가 내보낸 것과 손으로 쓴 XML 로 시험하고, Word 확인은 사용자에게 맡긴다.
- op 가 18개가 된다. 작은 모델이 `comment` 인자와 `comment` op 를 헷갈릴 수 있다 → 손 테스트로 본다.

| E4 | 목차 넣기·새로 고치기 | "맨 앞에 목차 넣어 줘", "목차 갱신" | 없다 |
| E6 | 문서 정보 (제목·작성자·주제·키워드) | "문서 제목 속성을 바꿔" | 없다. 만들 때 제목·작성자만 적는다 |

하지 않는 것: 워터마크·문서 보호(E6 의 나머지, 수요가 적다 → 결정 10), 도형·SmartArt·차트 개체 고치기, 그림 자르기·회전·효과, 떠 있는 그림(`wp:anchor`)의 위치 바꾸기, 데이터로 차트 그림 만들기, 각주 번호 모양·구역별 각주 설정, PDF 로 내보내기(묶음 8).

### 16.2 도구 모양

새 도구 없이 `edit_document` 를 넓힌다. 묶음 6 처럼 op 를 더하고, 지우기는 하나로 묶는다.

| 새 `op` | 하는 일 | 주요 인자 |
|---|---|---|
| `insert_image` | 기준 문단 앞·뒤에 그림 문단을 넣는다 | `paragraph`, `position`, `image`, `width`, `new_text`(대체 글자), `caption` |
| `edit_image` | 그림 바꾸기·크기·대체 글자 | `image: "g2"`, 새 그림 `target`, `width`, `new_text` |
| `footnote` | `old_text` 뒤에 각주(또는 미주)를 단다 | `paragraph`, `old_text`, `new_text`(각주 내용), `endnote` |
| `delete_object` | 그림·각주·미주를 지운다 | `image: "g2"` / `"f3"` / `"e1"` |
| `set_header` / `set_footer` | 머리글·바닥글을 만들거나 바꾼다. `{쪽}`·`{전체 쪽}` 은 쪽 번호 필드 | `new_text`, `align`, `first_page` |
| `insert_toc` | 목차를 넣는다. 이미 있으면 다시 만든다 | `paragraph`, `position`, `levels` |
| `set_properties` | 문서 정보를 바꾼다 | `properties` (`title`·`author`·`subject`·`keywords`) |

- op 가 18개에서 26개로 는다 (16.13 위험).
- 새 인자는 `image`, `width`(cm), `caption`, `endnote`, `align`(`left`·`center`·`right`), `first_page`, `levels`, `properties` 이다. `image` 하나로 문서 안 개체 id(`g2`·`f3`·`e1`)와 넣을 그림의 출처를 함께 받는다.
- 각주 내용·글상자 글자·목차 글자는 새 op 없이 지금의 `replace`·`format` 으로 고친다 (16.4).
- 예시

```json
{"op": "insert_image", "paragraph": "p14", "position": "after", "image": "img:3f2a…", "width": 12, "new_text": "시스템 구성도", "caption": "그림 1. 시스템 구성도"}
{"op": "edit_image", "image": "g2", "width": 8}
{"op": "footnote", "paragraph": "p12", "old_text": "120억 원", "new_text": "출처: 2024년 사업보고서"}
{"op": "delete_object", "image": "f3"}
{"op": "set_footer", "new_text": "{쪽} / {전체 쪽}", "align": "center", "first_page": false}
{"op": "insert_toc", "paragraph": "p1", "position": "after", "levels": 2}
{"op": "set_properties", "properties": {"title": "2024 사업 계획", "keywords": "계획, 예산"}}
```

### 16.3 E5 그림

#### 보기

```
[p14] 구성은 다음과 같다.
[p15] [그림 g1]
      (그림 g1 · 12.0×8.0cm · 대체 글자 "시스템 구성도")
[p16] (캡션) 그림 1. 시스템 구성도
```

- 인라인 그림(`wp:inline`)과 떠 있는 그림(`wp:anchor`)을 문서 순서대로 `g1`, `g2` 로 센다. 본문 → 머리글 → 바닥글 순서이고, 문단 번호와 같은 방식이다. 보기에서는 `￼` 자리에 `[그림 g1]` 이 나오고, 문단 아래 줄에 크기(`wp:extent`, EMU → cm)와 대체 글자(`wp:docPr/@descr`)를 적는다.
- 도형·차트·SmartArt·수식은 지금처럼 `￼` 로 둔다. 그림인지는 `a:graphicData/@uri` 가 그림(`…/picture`)인지로 가린다.
- `old_text` 에는 `[그림 g1]` 을 넣지 못한다. 지금의 `￼` 규칙과 같다.

#### 넣을 그림의 출처 (결정 1)

| 출처 | `image` 값 | 어떻게 |
|---|---|---|
| 같은 문서의 그림 | `g2` | 그 그림의 관계 대상 파일을 그대로 다시 쓴다. 새 관계는 만들지만 파일은 복사하지 않는다 |
| 프로젝트 문서의 그림 요소 | `img:<요소 id>` | `document_elements.image_key` 의 원본을 저장소에서 받는다. `search_project` 결과의 그림 항목에 이 id 를 적어 준다 |

- 채팅에 올린 그림 파일은 받지 않는다. 지금 그림은 올릴 수 있는 형식(`SUPPORTED_EXTENSIONS`)이 아니다.
- 프로젝트 그림 원본은 WebP 다 (긴 변 1600px). 2019 이전 Word 는 WebP 를 보여 주지 못하므로 **넣을 때 PNG 로 바꾼다.** 이를 위해 Pillow 를 의존성에 더한다 (결정 2, `chore` 커밋). 크기를 읽을 때도 쓴다.
- 대화가 프로젝트에 속하지 않았거나 그 요소가 이 프로젝트의 것이 아니면 실패한다. 모델이 다른 프로젝트의 그림을 가져오지 못하게 막기 위해서다.

#### 넣기 (`insert_image`)

- 새 문단에 run 하나를 만들고, 그 안에 `w:drawing/wp:inline`(`pic:pic`, `a:blip r:embed`)을 넣는다. 파일은 `word/media/imageN.png` 로 두고, `document.xml.rels` 관계와 `[Content_Types].xml` 의 `Default Extension="png"` 를 더한다. 이미 있으면 다시 쓴다.
- 너비를 주지 않으면 본문 폭(`w:pgSz` − 여백, 기준 문단이 든 구역)과 그림 원래 폭(96dpi 기준) 중 작은 쪽을 쓴다. 높이는 비율을 따른다. 본문 폭보다 크게 주면 본문 폭으로 줄이고 결과에 알린다.
- 새 문단 서식: 기준 문단의 `w:pPr` 을 따르되 번호 목록·제목 스타일은 떼고 가운데 정렬로 한다. 머리글·바닥글·표 칸 안 문단도 기준으로 받는다 (칸이면 칸 안에 넣고, 너비는 칸 폭까지).
- `wp:docPr` 의 `id` 는 문서 안에서 유일하게(모든 부분의 `docPr` 최대값 + 1) 하고, `name="그림 N"`, `descr=` 대체 글자를 넣는다.
- `caption` 이 있으면 그림 문단 바로 뒤에 캡션 문단을 둔다. 스타일은 `Caption`(없으면 만든다, 표시 이름 `캡션`)이고, 글자는 받은 그대로 쓴다. 번호 필드(`SEQ`)는 쓰지 않는다 (결정 3).

#### 바꾸기 (`edit_image`)

- `target` 에 새 출처(`g3`·`img:…`)를 주면 그 그림의 `r:embed` 를 새 관계로 바꾼다. 상자 크기는 너비를 지키고, 높이를 새 그림 비율에 맞춘다. 옛 파일은 다른 곳에서 쓰지 않을 때만 관계와 함께 지운다.
- `width` 를 주면 `wp:extent` 와 `a:ext` 를 같은 비율로 바꾼다. `new_text` 를 주면 대체 글자를 바꾼다.
- 떠 있는 그림은 크기·대체 글자·바꾸기만 하고 위치는 그대로 둔다.

#### 지우기 (`delete_object` + `g2`)

- 그림이 든 run 을 지운다. 문단에 다른 글자가 없으면 문단째 지운다 (지금 `delete_paragraph` 규칙을 따름). 파일은 바꾸기와 같은 기준으로 정리한다.

### 16.4 E3 각주·미주·글상자

#### 보기

```
[p12] 2024년 매출은 120억 원[각주 f1]이다.
…
[p81] (각주 f1) 출처: 2024년 사업보고서
[p82] (미주 e1) 용어 설명은 부록 참고
[p83] (글상자 1 · p2 안) 2024년 11월
```

- 본문의 `w:footnoteReference`·`w:endnoteReference` 는 `[각주 f1]`·`[미주 e1]` 로 보인다. 고칠 수 없는 표시라는 점은 `￼` 와 같다. 번호는 Word 가 보여 주는 순서(본문 순서)로 매기고, XML 의 `w:id` 와는 다르다.
- 각주·미주·글상자 문단은 **바닥글 뒤에** 번호를 매긴다. 본문 번호가 지금과 같게 유지된다. 구분선 각주(`w:type="separator"`·`continuationSeparator`)는 뺀다.
- 글상자는 `w:txbxContent` 의 문단이다. 새 Word 용(`mc:Choice` 안 `wps:txbx`)만 센다. 옛 Word 용(`mc:Fallback` 안 `v:textbox`)은 같은 내용의 사본이라 보기에 넣지 않는다.

#### 고치기

- 각주·미주·글상자 문단은 머리글 문단처럼 일반 부분으로 다룬다. `replace`·`format`·`insert_paragraph`·`delete_paragraph`·추적 고치기가 그대로 된다. 다른 부분에 걸친 범위는 지금처럼 거절한다.
- 글상자를 고치면 **고친 뒤 `mc:Choice` 의 `w:txbxContent` 를 복사해 `mc:Fallback` 쪽을 갈아 끼운다.** 복사본의 `w14:paraId` 는 새로 매긴다. Fallback 이 없거나 구조가 다르면(`v:textbox` 안에 `w:txbxContent` 가 없음) 갈아 끼우지 않고 결과에 알린다.
- 각주 안의 각주 번호 표시(`w:footnoteRef`)는 `￼` 처럼 고칠 수 없는 자리로 둔다.

#### 달기 (`footnote`)

- `old_text` 가 그 문단에 한 번 나와야 하고, 그 끝 바로 뒤에 `<w:r><w:rPr><w:rStyle w:val="FootnoteReference"/></w:rPr><w:footnoteReference w:id="N"/></w:r>` 을 넣는다. run 이 나뉘는 방식은 `format` 과 같다.
- `footnotes.xml` 에 `<w:footnote w:id="N">` 을 더한다. 안의 문단은 `FootnoteText` 스타일이고, 첫 run 은 `footnoteRef`, 그 뒤가 내용이다. `new_text` 의 `\n` 은 각주 안 문단 나누기다.
- 부분이 없으면 묶음 5 의 `_create_part` 로 만든다. 구분선 각주 −1·0 을 함께 넣고, `settings.xml` 의 `w:footnotePr` 에도 등록한다 (Word 가 요구한다 🔍). 스타일(`FootnoteText`·`FootnoteReference`, 미주는 `EndnoteText`·`EndnoteReference`)이 없으면 만든다.
- `endnote: true` 면 미주로 같은 일을 한다.

#### 지우기 (`delete_object` + `f3`)

- 본문의 참조 run 과 `footnotes.xml` 의 항목을 지운다. 남은 각주 번호는 Word 가 다시 매긴다.

### 16.5 E4 머리글·바닥글·쪽 번호

#### `set_header` / `set_footer`

- `new_text` 를 머리글·바닥글 내용으로 쓴다. `\n` 은 문단 나누기, `\t` 는 탭이다. `{쪽}` 은 `PAGE` 필드, `{전체 쪽}` 은 `NUMPAGES` 필드가 된다. 필드는 `w:fldSimple` 로 쓰고, 캐시 값은 `1` 로 둔다. 쪽 번호 필드는 Word 와 LibreOffice 가 그릴 때마다 다시 계산하므로 문제없다.
- 적용 범위: 첫 구역의 `w:sectPr` 에 기본(`w:type="default"`) 참조를 둔다. 참조가 없는 뒤 구역은 앞 구역의 것을 물려받는다. 구역마다 다른 머리글이 있는 문서면 **모든 구역의 기본 머리글을 같은 내용으로** 바꾸고 결과에 구역 수를 알린다.
- 머리글이 없으면 새 부분(`word/headerN.xml`)을 만든다. 관계·내용 형식은 `_create_part` 로 등록하고, 스타일은 `Header`/`Footer`(없으면 만든다)이다.
- 이미 있으면 내용을 바꾼다. 단, **그림·도형·글상자가 든 머리글이면 실패한다** (로고를 말없이 잃지 않게 하기 위해서다). 이때는 "(머리글 1) 문단을 `replace`·`insert_paragraph` 로 고쳐라" 고 안내한다 (결정 5).
- `align` 은 문단 정렬이다 (기본: 머리글 왼쪽, 쪽 번호만 있는 바닥글 가운데).
- `first_page: false` 면 첫 쪽에는 이 머리글을 쓰지 않는다. `w:titlePg` 를 켜고, 빈 첫 쪽 머리글(`w:type="first"`)을 둔다. 표지에 쪽 번호를 빼 달라는 요청을 위한 것이다. 기본은 손대지 않는다.
- 짝수·홀수 쪽 머리글은 만들지 않는다. 이미 있으면 기본 머리글과 함께 바꾸고 결과에 알린다.
- 지금 "머리글·바닥글 안에서는 문단 넣기 거절" 인 op 중에 `insert_paragraph`·`delete_paragraph`·`insert_image` 는 머리글·바닥글 안에서도 되게 푼다. 위의 실패 안내가 의미를 가지게 하기 위해서다.

### 16.6 E4 목차 (`insert_toc`)

- 기준 문단 앞·뒤에 Word 목차 필드를 넣는다: `TOC \o "1-N" \h \z \u` (N = `levels`, 기본 3). 복합 필드(`fldChar begin` … `separate` … `end`)로 쓴다.
- **필드 결과(보이는 목차 글자)는 우리가 미리 채운다.** 지금 문서의 제목 문단(스타일 수준 1~N)을 차례로 `TOC1`~`TOCN` 스타일 문단으로 넣는다 (스타일이 없으면 만든다). 쪽 번호는 계산할 수 없으므로 비우고, `settings.xml` 에 `w:updateFields w:val="true"` 를 켠다. Word 가 열 때 "필드를 업데이트할까요?" 라고 물은 뒤 쪽 번호를 채운다. LibreOffice 는 미리 채운 글자를 보여 준다 🔍 (결정 6).
- 목차 앞에 "목차" 제목 문단을 둔다 (`TOCHeading`, 없으면 일반 굵게).
- 이미 목차 필드(`TOC` 로 시작하는 `instrText`)가 있으면 새로 넣지 않고 **그 결과 글자를 지금 제목으로 다시 만든다** (목차 갱신 요청을 위한 것이다). 위치 인자는 무시하고 결과에 알린다.
- 보기에서 목차 문단은 `(목차)` 라벨이 붙고 필드 결과라 고칠 수 없다 (지금 필드 규칙과 같다).

### 16.7 E6 문서 정보 (`set_properties`)

- `docProps/core.xml` 의 `dc:title`·`dc:creator`·`dc:subject`·`cp:keywords` 를 바꾼다. 없으면 부분을 만든다. `cp:lastModifiedBy` 는 작성자 이름(`DEFAULT_AUTHOR`), `dcterms:modified` 는 지금 시각이다.
- 보기 맨 위에 한 줄 `(문서 정보: 제목 "…" · 작성자 … · 키워드 …)` 를 둔다. 값이 없으면 줄을 뺀다.
- 고칠 때마다 `dcterms:modified` 를 갱신할지 → 하지 않는다. 지금은 바이트 동일 원칙(고치지 않은 항목은 그대로)을 따른다. `set_properties` 때만 바꾼다.

### 16.8 만들기·Markdown 넣기에서

`create_document` 와 `insert_markdown` 의 Markdown 에서도 그림과 각주를 받는다 (결정 7).

| Markdown | 결과 |
|---|---|
| `![구성도](img:<요소 id>)` | 16.3 의 `insert_image` 와 같은 그림 문단 (본문 폭) |
| `![설명](https://…)`, 그 밖의 주소 | 지금처럼 `[설명]` 글자 (외부 주소는 받아 오지 않는다) |
| `…120억 원[^1]` + `[^1]: 출처` | 각주 (`mdit-py-plugins` 의 footnote 플러그인, 의존성 추가) |

- 목차는 Markdown 표기로 받지 않는다. 만든 뒤 같은 대화에서 `insert_toc` 를 쓰게 시스템 프롬프트에 적는다.

### 16.9 변경 추적 모드에서

| op | 추적 |
|---|---|
| `insert_image` | 그림 run 과 캡션을 `w:ins` 로 감싸고, 새 문단 기호도 `w:ins` 로 표시한다 (`insert_paragraph` 와 같다) ✅ |
| `delete_object` 그림 | 그림 run 을 `w:del` 로 감싼다 ✅ |
| `edit_image` 바꾸기 | 옛 그림 run 을 `w:del` 로, 새 그림 run 을 `w:ins` 로 남긴다 |
| `edit_image` 크기·대체 글자 | 기록 없이 바꾸고 결과에 "추적되지 않음" 을 알린다 (Word 도 그림 크기는 추적하지 않는다 🔍) |
| `footnote` | 참조 run 과 각주 내용을 `w:ins` 로 남긴다 ✅ |
| `delete_object` 각주 | 참조 run 을 `w:del` 로 감싼다. 각주 내용은 수락할 때 지운다 ✅ |
| `set_header`/`set_footer` | 머리글 내용을 지움 + 넣음 기록으로 남긴다. 새 부분 만들기·참조 더하기는 기록하지 않는다 |
| `insert_toc` | 목차 문단을 넣음 기록으로 남긴다 |
| `set_properties` | 기록 없음 (Word 도 추적하지 않는다) |

- 수락·거절(`_review`)은 각주·미주·글상자 부분에도 적용한다 (묶음 2 가 본문·머리글만 돌았는지 확인한다 🔍). 추적으로 지운 각주 참조를 수락하면 각주 항목도 지운다.

### 16.10 결과·도구 설명·프롬프트

- 결과 예: `inserted image g3 (12.0×8.0cm) after p14`, `added footnote f2 after '120억 원' in p12`, `set the footer of 2 sections (page numbers: {쪽})`, `inserted a table of contents with 7 headings; Word fills in page numbers when the document is opened`.
- `search_project` 결과의 그림 항목에 `image: img:<id>` 를 적는다 (결과에 정보를 더할 뿐이고 동작은 바뀌지 않는다).
- 범례: `[그림 g1]`·`[각주 f1]`·`[미주 e1]`·`(각주 f1)`·`(글상자 n · pX 안)`·`(목차)`·`(문서 정보 …)` 를 설명한다.
- 시스템 프롬프트: 그림은 같은 문서의 그림이나 프로젝트 문서의 그림만 넣을 수 있고, 다른 그림은 못 한다고 답한다. 쪽 번호는 `{쪽}` 으로 쓴다. "그림은 아직 못 한다" 는 문구를 고친다.

### 16.13 위험

- **op 가 26개가 된다.** 작은 모델이 `image` 인자(개체 id·출처 겸용)를 헷갈리거나 op 를 잘못 고를 수 있다. 도구 설명에 op 별 한 줄 예시를 두고, 손 테스트로 본다. 많이 틀리면 결정 4 의 다른 안(새 도구)으로 나눈다.
- 그림 XML(`wp:inline`)은 필수 자식·순서가 많다. 빠지면 Word 가 "읽을 수 없는 내용" 을 낸다. Word 가 만든 그림 XML 을 틀로 쓰고 `assert_valid` 로 검사한다. LibreOffice 는 잘못된 파일도 연다.
- 각주 부분을 새로 만들 때 Word 가 요구하는 구분선 각주와 `settings.xml` 등록이 확실하지 않다 🔍 → 1단계 실험에서 Word 가 만든 파일과 비교하고, 사용자가 Word 로 확인한다.
- `updateFields` 는 Word 를 열 때마다 물음 창을 띄운다. 사용자가 싫어할 수 있다 → 결과·답에 알린다. 한 번 업데이트하고 저장하면 Word 가 꺼 준다 🔍.
- 글상자 사본은 Fallback 쪽 서식(VML)을 잃을 수 있다. 옛 Word 만 보는 것이라 영향은 작다.
- 보기에 그림·각주 줄이 늘어 보기 결과가 길어진다. 그림 설명 줄은 크기·대체 글자만 적고 짧게 유지한다.
- 프로젝트 그림을 저장소에서 받아 오므로 `edit_document` 가 처음으로 DB·저장소를 읽는다. 권한 범위(그 프로젝트)를 테스트로 고정한다.
