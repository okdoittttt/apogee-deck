# 02-1. DOCX 고도화: 쓸만한 Word 편집 에이전트

`02.docx.md`(2단계: DOCX 글자 바꾸기) 다음 작업. PPTX(3단계)로 넘어가기 전에 DOCX 편집을 실제로 쓸만한 수준까지 넓힌다.
이 문서는 **조사 결과와 고도화 범위·설계 방향**을 정리한다. 2단계 구현 코드(`backend/app/documents/editing/docx.py`)를 기준으로 썼다.

## 2. 조사: 다른 제품은 어떻게 하나

### 2.1 Open WebUI

**본체에는 기존 docx 를 고치는 기능이 없다.** "Open WebUI 는 문서 편집이 된다" 는 인상은 아래 세 가지가 섞인 것이다.

#### 노트 (Notes, 본체)

- 자체 리치텍스트 편집기. docx 파일이 아니라 앱 안의 문서다.
- 선택한 부분을 AI 가 그 자리에서 고쳐 쓴다 (Enhance).
- 에이전트용 도구: `write_note`(전체 쓰기), `replace_note_content`(`replace_text` 로 일부 바꾸기). **우리 `edit_document` 의 `old_text`/`new_text` 와 같은 방식**이다.
- 안전장치
  - AI 가 내용을 넣기 **전에 버전을 먼저 남긴다**. 되돌리기가 된다.
  - 모델이 읽은 뒤 내용이 바뀐 노트는 **수정을 거절한다** (stale read 방지).
- 메모(코멘트), 공동 편집이 된다.
- 없는 것: docx 로 내보내기 (사용자 요청이 discussion #20420 으로 올라와 있다), 변경 내용 추적, 비교 화면.

#### Open Terminal (본체)

- AI 가 샌드박스에서 python-docx 코드를 짜서 **새** docx·pptx·xlsx 를 만든다. 채팅에 미리보기와 다운로드를 붙인다.
- 기존 docx 를 고치는 사용 사례는 문서에 없다. Word 파일은 미리보기만 한다.
- 에이전트가 고친 파일(코드·텍스트)은 diff 로 보여 준다.

#### 커뮤니티 도구 "Edit Office Files"

함수 52개짜리 도구. 기능 목록으로 참고하기 좋다.

| 묶음 | 기능 |
|---|---|
| 글자 | 서식을 지키는 찾아 바꾸기, 끝에 덧붙이기 |
| 검토 | **변경 내용 추적으로 고치기 (작성자 지정)**, 변경 추적 수락·거절, **메모 달기** |
| 만들기 | 템플릿, 편지 병합(mail merge), 머리글·목차·서명이 든 문서 |
| 문서 속성 | 워터마크, 문서 보호, 메타데이터 |
| 관리 | 문서 비교, 버전 관리, MD·HTML 로 내보내기 |

#### 커뮤니티 도구 "Generate Documents"

- Markdown 이나 JSON 을 받아 docx 를 만든다. 생성만 한다.
- 템플릿 7종(보고서, 제안서, 회의록 등), 표지·목차·표 스타일.
- 첨부한 docx 의 **레터헤드(머리글·바닥글)를 재사용**한다. "회사 양식에 맞춰 만들어 줘" 요구에 맞는 기능이다.

### 2.2 Microsoft Word Copilot

- Edit with Copilot: 문서 안에서 만들기, 고쳐 쓰기, 서식, 요약, 재구성, 어조 바꾸기, **글을 표로 바꾸기**, 그림 넣기.
- 흐름: 선택 → **미리보기** → `바꾸기` / `아래에 넣기` / `다시 만들기`. 사용자가 고르기 전에는 문서가 바뀌지 않는다.
- Word 의 변경 내용 추적이 켜져 있으면 **Copilot 이 고친 것도 추적으로 남는다.**
- Agent Mode: 여러 단계에 걸친 문서 작업(구조 잡기, 여러 곳 고치기)을 대화로 한다.
- 새 파일은 만들지 못한다 (열린 문서 안에서만).

### 2.3 ChatGPT (Word 추가 기능, "View and edit DOCX files" 앱)

- 선택한 글을 **문서 스타일을 지키며** 고쳐 쓰기, 서식 적용, **표 편집**, 쪽 설정.
- DOCX 앱은 올린 파일을 고쳐 **고친 사본을 내려받게** 한다. 우리 수정본 방식과 같다.
- 복잡한 서식·표·차트는 손으로 고쳐야 할 수 있다고 도움말에서 스스로 밝힌다.

### 2.4 Google Gemini in Docs

- 선택한 부분 Refine(고쳐 쓰기), 어조·길이 바꾸기.
- **Match doc format**: 새로 만드는 내용을 원본 문서 서식에 맞춘다.
- Fill with Gemini: 표 칸을 채운다.
- 서식·구조를 원본에 맞추는 것을 핵심 기능으로 내세운다.

### 2.5 Claude docx 스킬 (Anthropic)

- 새로 만들기, 고치기, 분석.
- 고칠 때 **변경 내용 추적(`w:ins`·`w:del`, 작성자 지정)** 으로 남기는 것을 기본으로 권한다. 메모 달기, 모든 변경 수락.
- 문서 검토 작업에서는 추적·메모가 기본 동작이라는 근거.

### 2.6 참고 라이브러리

| 이름 | 쓸모 |
|---|---|
| `docx-revisions` (PyPI) | python-docx 위에서 변경 추적(`w:ins`/`w:del`) 읽기·쓰기. B1·B3 구현 참고 |
| `docx-mcp-server` (PyPI) | MCP 로 docx 편집 기능을 노출. 도구 나누는 방식 참고 |

우리는 ZIP + lxml 직접 방식(2단계 결정 5)이라 라이브러리를 그대로 쓰지 않고 XML 구조만 참고한다.

## 3. 공통 패턴과 우리에게 주는 교훈

| 패턴 | 어디서 | 우리 상태 |
|---|---|---|
| **구조(문단·표)를 다룬다** | Copilot, ChatGPT, Gemini, 커뮤니티 도구 모두 | ❌ 글자만 바꾼다 |
| **사람이 검토할 수 있게 보여 준다** (변경 추적, 미리보기, 메모, diff) | Copilot(추적·미리보기), Claude 스킬(추적·메모), Open WebUI(버전·diff) | △ 수정본·답변 요약뿐 |
| **새 문서를 서식에 맞춰 만든다** | Open WebUI(Terminal, Generate Documents), Gemini(Match doc format) | ❌ TXT·MD·CSV 만 |
| **고치기 전에 되돌릴 곳을 남긴다** | Open WebUI 노트 | ✅ 수정본이 새 행이라 원본은 그대로 |
| **오래된 내용을 고치지 않게 막는다** | Open WebUI 노트(stale read 거절) | ❌ 이전 수정본도 그냥 고친다 |
| **원본 서식을 지킨다** | 모든 제품이 내세움, 그러나 "복잡한 서식은 깨질 수 있음" 단서 | ✅ 2단계의 강점 (바꾼 글자 말고는 그대로) |

정리하면, 우리 에이전트는 **원본 보존은 경쟁 제품보다 낫지만 할 수 있는 일의 폭이 좁다.** 고도화는 폭을 넓히되 "바꾼 곳 말고는 그대로" 원칙을 지키는 방향이어야 한다.

### 4.2 A. 구조 고치기

지금 가장 자주 막히는 부분이다. 구조를 바꾸면 **문단 번호가 밀린다**는 공통 문제가 있다 (6.3절).

#### A1. 문단 나누기·합치기 (P0)

- 요청 예: "덩어리진 문단을 세 문단으로 나눠 줘", "이 두 문단을 하나로 합쳐 줘".
- 나누기: `new_text` 의 `\n` 자리에서 문단을 나눈다.
  - 새 문단은 원래 문단의 `w:pPr`(스타일·들여쓰기·번호)을 복사한다.
  - 나누는 자리에 걸친 run 은 둘로 쪼개고 `w:rPr` 를 양쪽에 복사한다.
  - `w:pPr` 안의 `w:sectPr`(구역 나누기)는 **마지막 조각에만** 남긴다. 복사하면 구역이 늘어난다.
  - 문단 ID(`w14:paraId`, `w14:textId`)는 문서 안에서 유일해야 하므로 복사본에서는 지우거나 새로 만든다.
  - 거절: 나누는 자리가 링크·콘텐츠 컨트롤·필드 안이거나, 변경 추적 문단이거나, 표 칸 경계를 넘을 때.
  - `\n\n`(빈 줄)은 문단 하나 나누기로 본다. 빈 문단을 만들지 않는다.
- 합치기: 뒤 문단의 run 을 앞 문단 끝으로 옮기고 뒤 문단을 지운다.
  - 앞 문단의 `w:pPr` 를 쓴다. 뒤 문단에 `w:sectPr` 가 있으면 거절한다 (구역이 사라짐).
  - 다른 표 칸·다른 부분(본문과 머리글)에 걸치면 거절한다.
  - `old_text` 가 문단 경계를 넘는 지금의 거절("문단마다 따로")을 합치기로 풀 수 있다.
- 🔍 `\n` 을 문단 나누기로 볼지 문단 안 줄바꿈(A6)으로 볼지 (9절 결정 2).

#### A2. 문단 넣기·지우기·옮기기 (P0)

- 요청 예: "결론 문단 하나 추가해 줘", "p7 은 빼 줘", "이 문단을 맨 앞으로".
- 넣기: `after: "p12"` 또는 `before: "p12"` 로 위치를 정한다.
  - 새 문단 서식은 **기준 문단의 `w:pPr` 와 첫 run 의 `w:rPr`** 를 따른다 (주변과 같은 모양). 제목 뒤에 넣는 본문이면 다음 본문 문단을 따르는 편이 자연스럽다 🔍.
  - 스타일을 직접 지정할 수 있게 한다 (E2 와 같은 스타일 이름표).
- 지우기
  - 표 칸(`w:tc`)에는 문단이 최소 하나 있어야 한다. 마지막 문단을 지우면 빈 문단을 남긴다.
  - `w:sectPr` 를 가진 문단은 거절하거나, 구역 정보를 앞 문단으로 옮긴다 🔍.
  - 책갈피·메모 범위의 시작만 지워지고 끝이 남지 않게, 지우는 문단 안의 `bookmarkStart`/`commentRangeStart` 짝을 같이 정리한다.
  - 그림·필드가 든 문단도 지울 수 있게 할지 🔍 (그림 관계는 남아도 Word 가 열 수 있다).
- 옮기기: 지우기 + 넣기. 같은 부분(본문 안) 안에서만.

#### A3. 표 행·열 넣기·지우기, 칸 채우기 (P0)

- 요청 예: "부산 행 추가", "합계 열 추가", "비고 열 지워 줘".
- 행 넣기: 기준 행(`w:tr`)을 복사하고 칸 안 글자를 비운 뒤 새 값을 넣는다. 칸 서식(테두리·배경·정렬)이 따라온다.
- 열 넣기: `w:tblGrid` 에 `w:gridCol` 을 넣고, 모든 행에 `w:tc` 를 넣는다. 표 전체 너비를 어떻게 나눌지 정해야 한다 🔍.
- 거절: 세로 병합(`w:vMerge`)·가로 병합(`w:gridSpan`)이 걸린 행·열. 처음에는 병합 없는 표만.
- 칸 채우기: 지금도 칸 안 글자는 바꿀 수 있지만 **빈 칸에는 `old_text` 가 없어 못 채운다.** 빈 칸(빈 문단)을 `paragraph` 로 지정해 글자를 넣는 방법이 필요하다.
- 보기에서 표를 행 단위로 묶어 보여 주면 에이전트가 행을 고르기 쉽다 🔍.

#### A4. 목록 항목 넣기·지우기 (P1)

- 회의록·기획서는 대부분 목록이다.
- 목록 문단은 `w:pPr/w:numPr`(`w:numId`, `w:ilvl`)로 번호를 갖는다. A2 로 같은 `w:numPr` 를 복사해 넣으면 **번호가 이어진다** (번호 글자는 Word 가 계산).
- 들여쓰기 수준 바꾸기는 `w:ilvl` 만 바꾸면 된다.
- 보기에서 목록 문단에 `(목록 2수준)` 같은 표시를 붙이면 좋다 🔍.

#### A5. 제목 단위(섹션) 옮기기·지우기·넣기 (P1)

- 요청 예: "2장과 3장 순서 바꿔 줘", "부록 빼 줘".
- 섹션 = 제목 문단부터 같은 수준 이상의 다음 제목 전까지. 제목 수준은 스타일(`Heading N`)이나 `w:outlineLvl` 로 안다.
- A2 의 여러 문단 버전이다. 표도 함께 옮겨야 한다 (문단만이 아니라 블록 단위).

#### A6. 문단 안 줄바꿈 넣기 (P1)

- `w:br` 를 run 안에 넣는다. 보기에서 지금도 `\n` 으로 보인다.
- 주소·서명처럼 "한 문단 안에서 줄만 바꾸기" 가 필요한 경우.

#### A7. 글 ↔ 표 바꾸기 (P2)

- Copilot 의 대표 기능. "이 목록을 표로 정리해 줘".
- 표를 새로 만드는 것이라 D1(만들기)의 표 생성 코드를 같이 쓴다.

### 4.3 B. 검토 흐름

업무용(계약서·보고서 검토)으로 쓰려면 필요하다.

#### B1. 변경 내용 추적으로 고치기 (P0~P1)

- Word 에서 "검토 → 변경 내용" 으로 하나씩 수락·거절할 수 있게 남긴다. 작성자는 "AI 에이전트" 🔍.
- 2단계의 diff 결과가 그대로 쓰인다.

```xml
<!-- "120억" → "135억" : 바뀐 부분 "20" → "35" 만 -->
<w:r><w:t>1</w:t></w:r>
<w:del w:id="101" w:author="AI 에이전트" w:date="2026-11-24T10:00:00Z">
  <w:r><w:rPr><w:b/></w:rPr><w:delText>20</w:delText></w:r>
</w:del>
<w:ins w:id="102" w:author="AI 에이전트" w:date="2026-11-24T10:00:00Z">
  <w:r><w:rPr><w:b/></w:rPr><w:t>35</w:t></w:r>
</w:ins>
```

- 지우기는 run 을 `w:del` 로 감싸고 `w:t` 를 `w:delText` 로 바꾼다. 넣기는 새 run 을 `w:ins` 로 감싼다.
- `w:id` 는 문서 전체(메모·책갈피와 별도로 변경 기록끼리) 유일해야 한다.
- 문단 나누기·넣기(A1·A2)도 추적하려면 문단 기호에 `w:pPr/w:rPr/w:ins` 를 단다. 처음에는 글자 바꾸기만 추적 🔍.
- 보기·찾기는 **추적을 수락한 모습**(ins 보임, del 숨김)으로 보여 준다. 지금 펼치기 규칙과 같다.
- 결정 3(추적 기록이 있는 문단은 거절)과 부딪친다. 우리가 남긴 추적 위에 다시 고치려면 이 거절을 풀어야 한다 (B3 과 함께).
- 켜고 끄는 방법 🔍: 도구 인자(`track_changes: true`), 사용자 설정, 원본에 `w:trackRevisions` 가 켜져 있으면 자동 (Copilot 방식).

#### B2. 메모 달기 (P1)

- "검토해 줘" 에 본문을 고치지 않고 의견만 남기는 방법. "이 수치는 근거가 필요합니다".
- 필요한 것
  - `word/comments.xml` 부분 (없으면 만들고 `[Content_Types].xml` override, `document.xml.rels` 관계 추가).
  - 본문에 `w:commentRangeStart` / `w:commentRangeEnd` + `w:commentReference` 를 가진 run.
  - 메모 `w:id` 유일, 작성자·날짜.
- 범위는 `old_text` 로 정한다 (찾기 규칙 그대로). 도구는 `edit_document` 의 수정 종류 `comment` 로 🔍.

#### B3. 기존 변경 추적 읽기, 수락·거절 (P1)

- 남이 검토한 문서를 올리면 지금은 그 문단을 아예 못 고친다.
- 보기에서 추적 내용을 보여 준다: `[p5] 매출은 {-120-}{+135+}억 원` 같은 표시 🔍.
- 수락: `w:ins` 를 벗기고 `w:del` 을 지운다. 거절: 반대. `w:moveFrom`/`w:moveTo`, 서식 변경(`w:rPrChange`, `w:pPrChange`)도 처리해야 한다.
- 범위: 문서 전체 수락·거절부터, 문단·작성자 단위는 나중에 🔍.

#### B4. 화면에서 원본·수정본 비교 (P1)

- Open WebUI 도 에이전트가 고친 내용을 diff 로 보여 준다. 지금은 답변 텍스트의 바뀐 글자 요약뿐이다.
- 도구 결과에 이미 바뀐 문단의 전/후가 있다. 이것을 구조화해 프런트에서 문단 단위 diff 로 그린다.
- 프런트 작업이 크다. F1(미리보기)과 같이 설계 🔍.

### 4.4 C. 문서 전체 작업

#### C1. 많이 고치기, 부분 실패 보고 (P0)

- "맞춤법 다 고쳐 줘", "'고객사' 를 '고객' 으로 통일" 처럼 수정이 수십 개면, 지금 규칙(하나라도 실패하면 전부 취소)에서는 한 번의 실수로 전부 날아가 재시도가 반복된다.
- 바꿀 규칙 🔍
  - (A) 성공한 수정만 적용해 수정본을 만들고 실패한 수정은 이유와 함께 돌려준다.
  - (B) 지금처럼 전부 아니면 취소, 대신 실패 목록을 한 번에 다 알려 준다 (첫 실패에서 멈추지 않음).
  - (C) 인자로 고른다 (`atomic: true` 가 기본).
  - 추천: **(A) 를 기본으로, 하나도 성공하지 못하면 수정본을 만들지 않는다.** 에이전트가 실패한 것만 다시 시도하면 된다.
- 문단 번호(`pN`)는 호출을 시작할 때의 번호로, `old_text` 는 앞 수정을 적용한 글자에서 찾는다 (9.1절에서 확정).

#### C2. 보기에서 찾기 (P1)

- 긴 문서(100쪽 이상)를 400문단씩 넘겨 보면 토큰과 시간이 많이 든다.
- `view_document_for_edit` 에 `query` 를 더한다: 글자가 든 문단만 문단 번호와 함께, 필요하면 앞뒤 한 문단씩.
- 텍스트 형식(TXT·MD·CSV)에도 같이 쓸 수 있다 (줄 단위).

#### C3. 문단 고쳐 쓰기에서 서식 유지 (P1)

- 번역·어조 바꾸기처럼 문단이 거의 다 바뀌면, 결정 8(같은 글자 절반 미만이면 통째로)에 따라 새 글자 전체가 첫 조각 서식을 따른다. 문단 안의 굵은 단어·링크가 사라질 수 있다.
- 개선 방향 🔍
  - 글자 대신 **낱말 단위 비교**로 바꿔 살아남은 낱말의 서식을 지킨다.
  - 서식 있는 조각(굵게·링크)이 새 글에도 그대로 나오면 그 자리에 서식을 다시 입힌다.
  - 에이전트가 서식을 표시해 보내게 한다 (예: `**135억**`). E1 과 겹친다.
- 링크 안 글자가 통째로 바뀌는 경우는 지금도 링크 경계 규칙으로 막힌다.

#### C4. 최신 수정본 확인 (P1)

- 수정본이 쌓이면 에이전트가 v2 를 고친 뒤 v1 을 또 고쳐 갈래가 생길 수 있다.
- 고치려는 문서보다 **revision 이 큰 수정본이 같은 대화에 있으면** 거절하거나 경고하고 최신 document_id 를 알려 준다 🔍.
- Open WebUI 노트의 "읽은 뒤 바뀐 페이지는 거절" 과 같은 목적. 구현이 쉽다 (서비스에서 조회 한 번).

### 4.5 D. 만들기 (원래 7단계)

#### D1. Markdown → 새 docx (P0)

- Open WebUI(Terminal, Generate Documents)의 핵심 기능이다. 지금은 "Word 로 만들어 줘" 에 MD 를 권한다.
- 넣을 것: 제목 1~3, 문단, 굵게·기울임·링크, 글머리표·번호 목록, 표, 인용, 쪽 나누기.
- **한글 글꼴**: `w:rFonts` 의 `w:eastAsia` 를 맞춰야 한다 (2단계 시험 문서에서 OpenSymbol 로 잡혀 깨진 경험).
- 방법 🔍
  - (A) 빈 기본 템플릿 docx(스타일·번호 정의만 든 것)를 저장소에 두고, 본문 XML 만 lxml 로 만들어 넣는다. 2단계 코드와 같은 방식, 의존성 없음.
  - (B) python-docx 를 생성용으로만 넣는다 (2단계 결정 5 는 편집용 기준).
  - (C) Pandoc 같은 외부 변환기. 이미지가 커지고 운영 부담.
  - 추천: **(A)**. 목록 번호(`numbering.xml`)와 표 스타일을 템플릿에 미리 정의해 두면 본문만 만들면 된다.
- 기존 `create_document`(1단계, TXT·MD·CSV 만들기)에 형식 `docx` 를 더하는 방향.

#### D2. 양식·템플릿 채우기 (P1)

- 한국 업무 문서는 양식이 정해진 경우가 많다 (품의서, 회의록, 보고서 양식).
- 두 가지
  - **자리 바꾸기**: 양식 안의 `{{이름}}` 같은 자리를 값으로 바꾼다. 자리 글자가 run 여러 개로 쪼개져 있어도 2단계 펼치기로 찾을 수 있다. 사실상 `replace_all` 묶음이다.
  - **양식 위에 본문 쓰기**: 올린 docx 의 머리글·바닥글·스타일을 그대로 두고 본문만 D1 처럼 채운다 (Generate Documents 의 레터헤드 재사용).
- 표 행을 값 개수만큼 늘리는 경우(품목 목록)는 A3 행 넣기를 쓴다.

#### D3. 다른 형식으로 내보내기 (P2)

- DOCX → PDF, DOCX → MD. PDF 는 서버에 LibreOffice + 한글 글꼴이 필요하다 (이 맥의 headless LibreOffice 는 한글을 그리지 못했다. 컨테이너에서는 글꼴 패키지를 넣으면 될 수 있다 🔍).
- DOCX → MD 는 이미 xberg 파싱 결과(`content`)가 있다.

## 6. 도구 설계 방향

### 6.1 도구를 늘리지 않는다

`edit_document` 의 수정 하나에 **종류(`op`)** 를 붙여 넓힌다. 새 도구(`split_paragraph`, `insert_table_row` …)를 따로 만들지 않는다.

| 이유 | |
|---|---|
| 모델이 고를 도구가 늘지 않는다 | 도구가 많을수록 작은 모델(로컬 Ollama)이 엉뚱한 도구를 고른다 |
| 규칙을 그대로 쓴다 | "한 번 부르면 수정본 하나", 수정 목록을 한꺼번에 받는 구조 |
| 섞어 쓸 수 있다 | "p3 을 나누고, p7 을 지우고, 표에 행 추가" 를 한 번에, 수정본 하나로 |

### 6.2 수정 종류 (안)

초안. 묶음 1 에서 확정한 모양은 9.1절이다 (`split` 은 `replace` 의 `\n` 으로 합치고, 위치는 `position`·`target`, 표 행은 칸 안 문단 번호로 가리킨다).

```json
{ "op": "replace",          "old_text": "120억", "new_text": "135억", "paragraph": "p2" }
{ "op": "replace",          "old_text": "늘었다. 반면", "new_text": "늘었다.\n반면" }
{ "op": "merge",            "paragraph": "p5" }
{ "op": "insert_paragraph", "paragraph": "p12", "position": "after", "new_text": "결론적으로 …", "style": "본문" }
{ "op": "delete_paragraph", "paragraph": "p7" }
{ "op": "move_paragraph",   "paragraph": "p7", "position": "after", "target": "p2" }
{ "op": "insert_row",       "paragraph": "p23", "position": "after", "cells": ["부산", "18억"] }
{ "op": "delete_row",       "paragraph": "p27" }
{ "op": "comment",          "old_text": "135억", "paragraph": "p2", "new_text": "출처 확인 필요" }
```

- `op` 가 없으면 `replace` (지금 입력과 호환). 텍스트 형식은 `replace` 만.
- `comment` 는 묶음 2(B2).
- 종류가 늘수록 도구 스키마가 길어진다. 작은 모델이 따라오는지 fake 가 아닌 실제 모델로 확인해야 한다 🔍.

### 6.3 구조가 바뀌면 문단 번호가 밀린다

- 한 번 부를 때 받은 수정 목록의 `pN` 은 모두 **보기에서 본 번호(고치기 전 번호)** 로 해석한다.
- 적용은 문단 요소를 미리 붙잡아 두고(번호 → 요소) 순서대로 한다. 번호를 다시 세지 않는다. `old_text` 는 앞 수정을 적용한 글자에서 찾는다 (9.1절).
- 결과에 "문단 번호가 바뀌었으니 다시 보기로 확인하라" 를 붙인다. 다음 수정은 새 보기 기준.

### 9.1 묶음 1 상세 설계

#### 수정 종류 (`op`)

| `op` | 쓰는 필드 | 동작 |
|---|---|---|
| `replace` (기본) | `old_text`, `new_text`, `replace_all`, `paragraph` | 지금과 같다. `new_text` 의 `\n` 에서 문단을 나눈다 (A1). `old_text` 가 비고 `paragraph` 가 **빈 문단**(빈 표 칸 등)이면 그 문단에 `new_text` 를 채운다 (A3 칸 채우기) |
| `merge` | `paragraph` | `paragraph` 와 바로 다음 문단을 합친다. 경계 양쪽에 공백이 없으면 공백 하나를 넣는다 |
| `insert_paragraph` | `paragraph`, `position`, `new_text`, `style` | 기준 문단 앞(`before`)이나 뒤(`after`, 기본)에 새 문단을 넣는다. `\n` 이면 여러 문단 |
| `delete_paragraph` | `paragraph` | 문단을 지운다 |
| `move_paragraph` | `paragraph`, `position`, `target` | 문단을 `target` 문단 앞이나 뒤로 옮긴다 (서식 그대로) |
| `insert_row` | `paragraph`, `position`, `cells` | `paragraph` 가 든 표 행의 앞이나 뒤에 행을 넣고 `cells` 값을 칸마다 넣는다 |
| `delete_row` | `paragraph` | `paragraph` 가 든 표 행을 지운다 |

- 텍스트 형식(TXT·MD·CSV)은 `replace` 만 받는다. 다른 `op` 는 그 수정만 실패로 돌려준다.
- 표 열 넣기·지우기, 목록 수준 바꾸기, 문단 안 줄바꿈은 묶음 1 에서 빼고 뒤로 미룬다.

#### 문단 번호와 수정 순서

- 수정 안의 `pN`(`paragraph`, `target`)은 모두 **이번 호출을 시작할 때의 번호**(에이전트가 본 보기 번호)다. 앞 수정이 문단을 나누거나 지워도 뒤 수정의 `p7` 은 원래 p7 문단을 가리킨다.
  - 구현: 호출을 시작할 때 문단 요소마다 번호 표시(임시 속성)를 달고, 끝나면 지운다. 나눈 문단의 앞 조각이 원래 요소다.
  - 지워진 문단을 가리키면 그 수정은 실패.
- `old_text` 는 지금처럼 **앞 수정을 적용한 글자**에서 찾는다 (1단계와 같은 규칙).
- 결과에 구조가 바뀌었으면 "문단 번호가 바뀌었으니 새 수정본은 다시 보기로 확인하라" 를 붙인다.

#### 수정마다 따로 성공·실패 (C1)

- 수정 하나를 적용하기 전에 문서 상태를 저장해 두고, 그 수정이 실패하면 그 수정만 되돌린다 (`replace_all` 이 문단 여러 개를 고치다 실패해도 그 수정 전체가 취소).
- 결과: 성공한 수정의 바뀐 곳 요약 + 실패한 수정의 이유. 하나도 성공하지 못하면 지금처럼 오류("No changes were saved").
- CSV 검사와 "빈 문서가 된다" 검사는 모든 수정을 적용한 뒤 한 번 한다 (실패하면 전부 취소).

#### 문단 나누기 (A1)

- `\n\n` 처럼 이어진 줄바꿈은 하나로 본다. 나눈 결과에 **글자 없는 문단이 생기면 거절**한다 (빈 문단 넣기는 `insert_paragraph` 로도 하지 않는다).
- 새 조각은 원래 문단의 `w:pPr` 를 복사한다. `w:pPr` 안의 `w:sectPr`(구역 나누기)는 마지막 조각으로 옮긴다. 원래 요소의 속성(`w14:paraId` 등)은 복사하지 않는다.
- 나누는 자리의 run 은 둘로 쪼개고 `w:rPr` 를 복사한다. 나누는 자리 뒤의 형제 요소(run, 링크, 책갈피)는 새 조각으로 옮긴다.
- 거절: 나누는 자리가 링크·콘텐츠 컨트롤 등 묶음 안일 때, 복합 필드 안일 때.

#### 문단 넣기·지우기·옮기기 (A2, A4)

- 새 문단 서식: 기준 문단의 `w:pPr`(구역 나누기·변경 기록 빼고)와 첫 글자 run 의 `w:rPr`. 목록 문단이면 `w:numPr` 가 따라와 **번호가 이어진다** (A4).
  - 기준 문단이 제목이고 뒤에 넣으면, 다음 문단이 제목이 아닐 때 그 문단을 기준으로 삼는다 (제목 뒤에 넣는 글은 보통 본문).
  - `style` 을 주면 `w:pPr` 는 그 스타일만 두고 run 서식은 복사하지 않는다. 받는 값: `제목 1`~`제목 9`, `본문`(스타일 없음 = 기본), `문서 제목`, `부제목`, 또는 문서의 스타일 이름. 문서에 없는 스타일이면 실패.
- 지우기 거절: 구역 나누기(`w:sectPr`)를 가진 문단, 메모가 달린 문단, 복합 필드가 문단 밖으로 이어지는 문단, 변경 추적 문단. 책갈피는 짝(시작·끝)을 함께 지운다.
- 표 칸·본문의 마지막 문단이라 지우면 구조가 깨지면(칸에 문단이 없어지거나 표가 칸의 끝이 됨) 지우지 않고 **글자만 비운다**.
- 옮기기는 같은 부분(본문, 머리글 하나) 안에서만. 지우기와 같은 거절 조건.
- 보기에 목록 문단 표시 `(목록)`, `(목록 2수준)` 을 붙인다.

#### 표 행 넣기·지우기 (A3)

- 기준 행을 복사하고 칸마다 첫 문단의 `w:pPr`·첫 run 의 `w:rPr` 만 남겨 `cells` 값을 넣는다. 칸 수보다 값이 적으면 나머지 칸은 비운다. 많으면 실패.
  - 기준 행이 머리글 행(`w:tblHeader`)이고 아래 행이 있으면 아래 행을 복사한다. 복사본에서 `w:tblHeader`·`w:cnfStyle` 은 뺀다.
- 거절: 기준 행이나 넣는 자리 바로 아래 행에 세로 병합(`w:vMerge`)이 있을 때, 변경 추적 행, 표의 마지막 한 행 지우기, 메모가 달린 행 지우기.

#### 최신 수정본 확인 (C4)

- 고치려는 문서를 원본으로 만든 수정본(`source_document_id` 가 이 문서)이 같은 대화에 있으면 거절하고, 그 사슬의 마지막 수정본 document_id 를 알려 준다.
- 보기 도구는 막지 않는다 (예전 버전을 보는 것은 괜찮다).

- **`set_style`** (2026-11-24): 이미 있는 문단을 `제목 N`·`본문`·`문서 제목`·`부제목`·문서의 스타일 이름·`목록`/`목록 N수준` 으로 바꾼다.
  보기의 표시와 같은 말을 받는다. 제목·본문으로 바꾸면 목록 번호를 떼고, 목록이 아닌 문단을 목록으로 바꾸면 바로 앞·뒤 목록에 이어 붙인다 (새 목록 만들기는 안 됨).
- **보기의 `(빈 칸)`**: 빈 표 칸을 채우려면 그 문단 번호가 필요해서, 표 칸의 빈 문단만 보여준다.

### 11.1 목표와 범위

| B3 | 남이 남긴 변경 추적 기록 **보기**, 수락·거절 | ✅ 먼저 (B1 이 이 위에 선다) |
| B1 | 에이전트의 수정을 **변경 추적으로 남기기** | ✅ |

순서를 B3 → B1 → B2 로 하는 이유: 지금은 추적 기록이 있는 문단을 거절한다(결정 3). B1 로 추적을 남기면 다음 수정에서 우리 문단을 우리가 못 고치게 되므로, 추적 기록을 읽고 다루는 B3 이 먼저 있어야 한다.

### 11.2 지금 상태

- 펼치기(`_flatten`): `w:ins`·`w:moveTo` 글자는 보이고, `w:del`·`w:moveFrom` 은 숨긴다 (수락한 모습). 그런 문단은 `tracked=True`.
- 보기: `(변경 추적 기록 있음 · 고칠 수 없음)` 표시. 수정: 그 문단을 건드리는 모든 `op` 거절 (`_check_untracked`, 표 행도 같음).
- 메모: 읽지도 보여주지도 않는다. 메모가 달린 문단·행 지우기는 거절한다. 메모 범위 표시(`commentRangeStart` 등)는 펼칠 때 무시한다.
- 서식 복사(`_without_tracking`)는 `w:rPrChange`·`w:pPrChange` 등을 지운다.
- 🔍 파서(`xberg`)가 추적 기록이 있는 DOCX 의 `content` 에 지운 글자를 넣는지 모른다. 구현 1단계에서 확인한다.

### 11.3 B3 기존 변경 추적 기록 보기·수락·거절

#### 보기

추적 기록이 있는 문단만 표시를 바꾼다. 나머지 문단은 지금과 같다.

```
[p5] (변경 추적: 김민지) 매출은 {-120-}{+135+}억 원이다.
[p9] (변경 추적: 김민지 · 서식 바뀜) 결론
```

- 넣은 글자 `{+…+}`, 지운 글자 `{-…-}`. 옮긴 글자(`moveFrom`/`moveTo`)도 각각 `{-…-}`/`{+…+}` 로 보인다.
- 서식만 바뀐 것(`rPrChange`·`pPrChange`)은 글자로 보여줄 수 없어 라벨만 붙인다.
- 문단 기호의 추적(`w:pPr/w:rPr/w:ins|del`: 문단 나누기·합치기를 추적한 것)은 라벨 `문단 넣음·나눔 추적` · `문단 합침 추적` 으로.
- 범례에 표기 설명을 더한다. `{+`·`{-` 가 원래 글자에 있으면 헷갈리므로, 🔍 표기 대신 `⟦+…⟧` 같은 드문 기호를 쓸지 정한다.
- `old_text` 찾기는 지금처럼 **수락한 모습**(표기 없는 글자)에서 한다. 표기는 보기에만 있다. 🔍 모델이 표기째 복사하는 실수에는 힌트를 준다 (`[L12]` 힌트와 같은 방식).

#### 수락·거절

새 `op` 두 개: `accept_changes`, `reject_changes`.

| 인자 | 뜻 |
|---|---|
| `paragraph` (선택) | 이 문단만. 없으면 문서 전체 |
| `author` (선택, 🔍) | 이 사람이 남긴 것만 |

| 기록 | 수락 | 거절 |
|---|---|---|
| `w:ins` (글자) | 감싼 것만 벗긴다 | 안의 run 을 지운다 |
| `w:del` (글자) | 통째로 지운다 | 벗기고 `w:delText` → `w:t` |
| `w:moveTo` / `w:moveFrom` + 범위 표시 | ins/del 처럼 + 범위 표시 지움 | 반대 |
| `w:rPrChange` / `w:pPrChange` | 기록만 지운다 | 안의 옛 서식으로 되돌린다 |
| 문단 기호 `w:pPr/w:rPr/w:ins` | 기록만 지운다 | 다음 문단과 합친다 (문단 나누기 취소) |
| 문단 기호 `w:pPr/w:rPr/w:del` | 다음 문단과 합친다 | 기록만 지운다 |
| 표 구조(`w:trPr/w:ins·del`, `w:cellIns`·`cellDel`·`cellMerge`, `w:tblPrChange` 등), `w:sectPrChange`, `w:numberingChange` | ❌ 처음에는 거절 ("Word 에서 처리") | ❌ |

- 거절하는 기록이 범위 안에 하나라도 있으면 그 수정은 실패한다 (부분 적용하지 않는다, C1 수정 단위).
- 머리글·바닥글도 같은 규칙. 각주·미주·메모 본문 안의 추적은 건드리지 않는다.

#### 추적 기록이 있는 문단 고치기

결정 3(거절)을 좁힌다: **바꾸는 범위가 추적된 글자(`ins` 글자, 숨은 `del` 자리)에 닿지 않으면** 일반 글자처럼 고친다.
닿으면 지금처럼 거절하고 "먼저 수락·거절하라" 고 안내한다. 숨은 `del` 자리는 펼칠 때 길이 0 의 표시 글자로 기억해 경계를 판단한다.
구조 `op`(나누기·합치기·지우기·옮기기)는 추적 문단에서 계속 거절한다.

### 11.4 B1 변경 추적으로 고치기

#### 켜는 방법

`edit_document` 에 호출 단위 인자 `track_changes: bool | None` 을 더한다 (수정마다가 아니라 한 번에 하나의 수정본이므로).

| 값 | 동작 |
|---|---|
| `true` | 추적으로 남긴다. 사용자가 "변경 추적으로", "검토할 수 있게", "고친 곳 표시해서" 라고 했을 때 |
| `false` | 바로 고친다 (지금과 같음) |
| 없음 (기본) | 원본 `word/settings.xml` 에 `w:trackRevisions` 가 켜져 있으면 추적, 아니면 바로 고친다 (Copilot 방식) |

- 추적 모드에서 추적할 수 없는 수정은 **추적 없이 몰래 적용하지 않고 실패**시킨다 (사용자가 Word 에서 수락·거절할 수 있다고 믿기 때문이다).
- 원본의 `w:trackRevisions` 설정은 바꾸지 않는다.

#### 작성자·날짜·ID

- `w:author`: 🔍 설정값 하나 (`EDIT_AUTHOR`, 기본 `"AI 에이전트"`). 사용자 이름을 쓰면 사람이 고친 것과 구분이 안 된다.
- `w:date`: 호출 시각(UTC, 초 단위) 하나를 그 호출의 모든 기록에 쓴다. Word 는 같은 작성자·시각 기록을 묶어 보여준다.
- `w:id`: 문서 전체(본문·머리글·바닥글·각주)에서 쓰이는 변경 기록 id 의 최댓값 + 1 부터. 메모·책갈피 id 와 겹쳐도 되지만, 안전하게 모든 `w:id` 의 최댓값을 기준으로 한다.

#### 수정 종류별 추적 방법

| `op` | 추적 방법 | 1차 구현 |
|---|---|---|
| `replace` | 바꾸기 알고리즘의 diff 결과에서 지울 글자는 run 을 잘라 `w:del` + `w:delText`, 넣을 글자는 새 run 을 `w:ins` 로 감싼다. 서식은 지금 규칙 그대로 | ✅ |
| `replace` 의 `\n` (나누기) | 나뉜 앞 문단의 문단 기호에 `w:pPr/w:rPr/w:ins` | ✅ |
| `insert_paragraph` | 새 문단의 run 을 `w:ins`, 문단 기호에 `w:ins` | ✅ |
| `delete_paragraph` | run 을 모두 `w:del`, 문단 기호에 `w:del` (문단은 남는다) | ✅ |
| `merge` | 앞 문단 기호에 `w:del` (+ 넣은 공백은 `w:ins`) | 🔍 |
| `set_style` | `w:pPrChange` 에 옛 `w:pPr` 를 넣는다 | 🔍 |
| `insert_row` / `delete_row` | `w:trPr/w:ins` / `w:trPr/w:del` + 칸 글자 ins/del | 🔍 |
| `move_paragraph` | `moveFrom`/`moveTo` + 범위 표시 (이름·id 짝) | ❌ 처음에는 추적 모드에서 거절 |

- 같은 호출 안에서, 또는 다음 호출에서 **우리가 넣은 글자(`w:ins`, 작성자가 우리)** 를 다시 고치면 Word 처럼 그 `ins` 안을 바로 고친다 (지운 기록을 남기지 않는다). 다른 사람의 추적 글자는 11.3 규칙대로 거절.
- 결과 요약은 지금과 같고 끝에 `(tracked)` 를 붙인다. 보기에서는 11.3 표기로 우리 수정도 보인다.
- 수정본 파싱 `content` 는 수락한 모습이어야 한다 (🔍 파서 확인, 아니면 파싱 전에 수락한 사본을 만들어 넘긴다).

### 11.5 B2 메모

#### 보기

메모가 달린 문단 아래에 메모를 보여준다.

```
[p12] 2024년 매출은 120억 원이다.
      (메모 c3 · 김민지: "근거 자료가 필요합니다" → '120억 원')
```

- 메모 id(`c3`) 를 보여줘서 "메모대로 고쳐 줘" 에서 모델이 어느 메모인지 가리킬 수 있게 한다.
- 메모 본문이 길면 자른다. 답글(`commentsExtended` 의 `paraIdParent`)은 🔍 처음에는 같은 줄에 `(답글 2개)` 만.

#### 달기

새 `op` `comment`.

| 인자 | 뜻 |
|---|---|
| `old_text` | 메모를 달 글자 (찾기 규칙은 `replace` 와 같다). 비우고 `paragraph` 만 주면 문단 전체 |
| `paragraph` (선택) | 찾을 문단 |
| `new_text` | 메모 내용 (🔍 필드 이름을 `comment` 로 따로 둘지) |

- 범위는 한 문단 안, 링크·콘텐츠 컨트롤 경계를 넘지 않는다 (나누기와 같은 제약). 경계에서 run 을 자르고 `w:commentRangeStart` / `w:commentRangeEnd` 를 넣은 뒤, 끝에 `w:commentReference` 를 가진 run 을 넣는다 (스타일 `CommentReference` 가 문서에 있으면 붙인다).
- `word/comments.xml` 이 없으면 만든다: `[Content_Types].xml` override, `word/_rels/document.xml.rels` 관계 추가. 있으면 `w:comment` 를 덧붙인다. 작성자·날짜는 B1 과 같다. `w:initials` 🔍.
- `commentsExtended.xml`·`commentsIds.xml`(새 Word 의 답글·해결 표시)은 만들지 않는다. Word 는 `comments.xml` 만으로 메모를 연다 🔍 (확인 필요).
- 고치지 않은 ZIP 항목은 지금처럼 그대로 복사한다. 새로 만드는 부분과 관계·내용 형식 파일만 바뀐다.
- 메모 답글·지우기·해결은 이번 묶음에서 빼고, 메모가 달린 문단 지우기 거절도 그대로 둔다 🔍.

### 11.8 위험

- Word 는 잘못된 추적·메모 XML 에 "읽을 수 없는 내용" 오류를 낸다 (id 중복, `w:del` 안의 `w:t`, 범위 짝 누락). 기계 확인과 Word 확인이 꼭 필요하다.
- 추적 모드의 수정은 diff 를 그대로 드러낸다. 지금 바꾸기는 비슷하지 않으면 통째로 바꾸는데(`WHOLE_REPLACE_RATIO`), 추적에서는 글자 단위로 쪼개진 기록이 읽기 어려울 수 있다 🔍 (단어 단위로 맞출지).
- 파일이 커질수록(추적 기록 누적) 보기가 길어진다. 보기 `max_chars` 안에서 표기가 차지하는 몫.
