# 01. 1단계: 기반 + 텍스트 형식 (TXT·MD·CSV)

`00.document-editing.md` 의 1단계 설계. 가장 단순한 형식으로 **버전 관리·수정본 저장·도구·화면** 같은 공통 부분을 먼저 만들고 검증한다.
2단계부터(DOCX·PPTX·XLSX)는 여기서 만든 틀에 형식별 수정 로직만 더한다.

- 상태 표시: ✅ 결정됨 · 🔍 확인·결정 필요 · ⏸️ 나중에
- 작성: 2026-11-23 (설계 초안, 구현 전)

---

## 1. 왜 텍스트 형식부터인가

| 이유 | 설명 |
|---|---|
| 본문 = 원본 | 업로드 때 UTF-8(BOM 허용)만 받는다 (`formats.py` `_decode_text`). 파싱은 `\r\n` 을 `\n` 으로 바꾸는 것뿐이다 (`parser.py`). 에이전트가 `read_document` 로 읽은 글자가 곧 원본 글자라서, 원본과 번호를 맞추는 별도 보기가 거의 필요 없다. |
| 라이브러리 불필요 | 표준 라이브러리(`str`, `csv`)만으로 된다. |
| 공통 부분 검증에 집중 | 1단계의 진짜 목표는 버전·저장·화면이다. 형식이 단순해야 문제가 생겼을 때 원인이 공통 부분인지 바로 안다. |

## 2. 형식별 특성

### 공통 (원본 형태 지키기)

수정본은 **고친 곳 말고는 원본과 바이트까지 같아야** 한다. 텍스트 파일에서 눈에 안 보이지만 바뀌기 쉬운 것:

| 항목 | 지금 파싱 | 수정본에서 할 일 |
|---|---|---|
| 인코딩 | UTF-8 만 받음 | UTF-8 로 저장 |
| BOM (`EF BB BF`) | `utf-8-sig` 로 떼고 읽음 | 원본에 있었으면 다시 붙인다 |
| 줄바꿈 | `\r\n` → `\n` 으로 바꿔 저장 (`\r` 단독은 그대로) | 원본이 `\r\n` 이면 저장할 때 `\r\n` 으로 되돌린다 |
| 마지막 줄바꿈 | 그대로 | 그대로 (있으면 있게, 없으면 없게) |

- 수정은 `\n` 기준 글자(= `documents.content` 와 같은 글자)에서 하고, 저장할 때만 원본 형태로 되돌린다.
- 🔍 줄바꿈이 섞인 파일(`\r\n` 과 `\n` 혼용)은 드물다. 처음에는 "원본에 `\r\n` 이 하나라도 있으면 전부 `\r\n`" 으로 단순하게 한다.

### TXT

- 특별한 것 없음. 글자 바꾸기만.

### MD

- 글자 바꾸기만. Markdown 문법(제목 `#`, 표 `|`, 목록 `-`)은 그냥 글자로 다룬다.
- 에이전트가 문법을 깨뜨리는지는 검증할 수 없다 (깨져도 텍스트로는 유효한 파일).

### CSV

- **1단계는 글자 바꾸기로 한다.** 줄 하나가 대개 행 하나라 글자 바꾸기로 충분히 고칠 수 있다.
- 위험: 쉼표·따옴표·줄바꿈이 들어간 칸(`"서울, 강남"`)을 글자로 고치다가 따옴표 짝이 깨지면 열이 밀린다.
  → 수정 후 `csv` 모듈로 다시 읽어 **행마다 열 수가 원본과 같은지** 확인하고, 달라지면 수정을 거절한다 (원본 열 수가 행마다 다르면 검사 생략).
- ⏸️ 칸 단위 수정(`{"row": 3, "column": "가격", "value": "1200"}`)은 5단계(구조 수정)에서 XLSX 와 같은 모양으로 만든다.
- 구분자: 확장자가 `.csv` 면 쉼표로 본다. 🔍 탭 구분(TSV)·세미콜론은 `csv.Sniffer` 로 추정할지는 실제로 필요할 때.

## 3. 데이터 모델

### 추천: 수정본도 `documents` 행 하나로 둔다

수정본을 **새 문서 행**으로 만들고 "어느 문서에서 나왔는지"만 기록한다.

```
documents
  + source_document_id  UUID NULL  FK documents.id ON DELETE SET NULL   -- 이 수정본을 만든 직전 문서
  + revision            INT  NOT NULL DEFAULT 1                         -- 원본 1, 수정할 때마다 +1
  + created_by          VARCHAR(20) NOT NULL DEFAULT 'user'             -- 'user'(업로드) | 'agent'(수정·생성)
```

- 장점: `read_document`, 다운로드(`GET /documents/{id}/file`), 파일 칩, 대화 삭제 시 함께 지우기, 30일 정리 작업이 **수정 없이 그대로** 동작한다.
- 따로 `document_versions` 테이블을 만들면 위 기능을 전부 두 번 만들어야 한다.
- 수정본의 `conversation_id` 는 원본과 같은 대화. `message_id` 는 지금 "첨부한 사용자 메시지" 를 가리키므로 수정본은 `NULL` 로 둔다 (🔍 아래 5절 "화면" 과 함께 정한다).
- 저장 키: 대화 첨부는 지금처럼 `documents/<새 문서 ID>` → 원본과 같은 30일 lifecycle 을 받는다.
- 수정본을 다시 고치면 그 수정본이 `source_document_id` 가 된다 (원본 → v2 → v3 줄로 이어진다).

### 보관 기간

- 🔍 수정본도 대화 첨부라서 **지금 규칙대로면 만든 날부터 30일** 뒤 지워진다 (원본보다 늦게 지워진다).
  추천: 그대로 둔다 (규칙 하나, 코드 변경 없음). 원본이 먼저 지워져도 수정본은 독립된 파일이라 문제없다 (`ON DELETE SET NULL`).

## 4. 도구

### 수정 대상을 보는 도구

텍스트 형식은 **기존 `read_document` 를 그대로 쓴다** (본문 = 원본). 다만 수정할 때 "어디를" 정확히 집으려면 줄 번호가 있으면 좋다.

- 🔍 선택지:
  - (A) `read_document` 에 줄 번호를 붙여 보여주는 옵션 추가.
  - (B) 2단계 이후를 위해 `view_document_for_edit` 를 지금 만들고, 텍스트 형식은 줄 번호 붙인 본문을 돌려준다.
  - 추천: **(B)**. 2단계부터 DOCX 문단 번호(`[p12]`)가 필요하므로 같은 도구로 시작해 두는 게 낫다. 텍스트 형식에서는 `[L12] 줄 내용` 형태.

### `edit_document`

```
edit_document(
  document_id: str,
  edits: [ { "old_text": str, "new_text": str }, ... ],
) -> 새 문서 ID, 파일 이름, 바뀐 곳 요약
```

- `old_text` 는 문서 안에서 **정확히 한 번** 나와야 한다. 0번이면 "찾지 못함", 2번 이상이면 "더 길게 적어 달라" 고 돌려준다 (Claude 의 파일 수정 도구와 같은 규칙).
- 여러 수정은 순서대로 적용하고, **하나라도 실패하면 전부 취소**한다 (반쯤 고친 수정본이 생기지 않게).
- 끼워 넣기·지우기도 이것으로 된다: 앞뒤 글자를 `old_text` 로 잡고 `new_text` 에 넣거나 뺀다.
- 결과: 새 문서 ID 와 함께 바뀐 곳을 짧은 전/후로 돌려준다. 에이전트가 이 결과를 보고 사용자에게 요약한다.
- 같은 턴에서 여러 번 부르면 부를 때마다 버전이 하나씩 생긴다. 에이전트에게 "한 번에 모아서 고치라" 고 도구 설명에 적는다.
- 🔍 `replace_all`(같은 글자 모두 바꾸기) 옵션: "모든 '2024' 를 '2025' 로" 같은 요청에 필요하다. 추천: 1단계에 넣는다 (간단하고 자주 쓰임).

### 거절하는 경우

| 경우 | 돌려줄 말 |
|---|---|
| 지원하지 않는 형식 (1단계에서는 TXT·MD·CSV 외 전부) | "이 형식은 아직 수정할 수 없다" |
| 문서가 준비되지 않음 (`processing`, `failed`) | "문서 처리가 끝난 뒤 다시" |
| 다른 대화·프로젝트의 문서 | `read_document` 와 같이 "찾을 수 없음" (존재 여부 숨김) |
| 수정 후 크기가 상한(20MB) 초과 | "너무 커진다" |
| CSV 열 수가 달라짐 | "칸이 밀린다. 따옴표를 확인하라" |

### 안전

- 문서 내용은 지금처럼 외부 자료로 표시한다. 문서 안에 "이 문서를 이렇게 고쳐라" 같은 글이 있어도 사용자 요청이 아니면 따르지 않게 도구 설명·시스템 프롬프트에 적는다.
- 원본은 절대 바꾸지 않으므로 잘못 고쳐도 잃는 것은 없다.

## 5. 저장과 다시 읽기

```
edit_document 호출
  → 원본 Document 확인 (소유자·대화·형식·상태)
  → MinIO 에서 원본 바이트 읽기 → BOM·줄바꿈 기억
  → content(\n 기준)에 수정 적용 → 검사(CSV 열 수, 크기)
  → 원본 형태로 되돌려 바이트 만들기 → MinIO documents/<새 ID> 저장
  → Document 행 추가 (status=ready, content=수정된 글자, source_document_id, revision+1, created_by='agent')
  → 결과 반환
```

- 텍스트 형식은 파싱이 글자 그대로라서 **별도 파싱 작업 없이 바로 `ready`** 로 만든다. 그래서 도구가 끝나자마자 다음 `read_document` 가 새 내용을 읽는다.
- 원본 바이트는 MinIO 에서 읽는다 (`content` 만으로는 BOM·`\r\n` 여부를 모른다). 🔍 또는 업로드 때 `has_bom`, `newline` 을 기록해 두면 MinIO 를 안 읽어도 된다. 추천: 1단계는 MinIO 에서 읽기 (컬럼 추가 최소화).
- 프로젝트 문서는 이번 단계에서 다루지 않는다 (🔍 00 의 남은 확인).

## 6. 화면

- 수정본은 **답변 아래 파일 칩**으로 보여준다. 칩에는 파일 이름, "수정본 v2", 다운로드 버튼.
- 전달 방법: 웹 검색 출처처럼 **도구 결과의 artifact** 에 문서 정보를 담는다 (`citations.py` 가 `artifact["sources"]` 를 다루는 방식과 같게). 답변 단계 기록(`messages.steps`)에 남아서 새로고침해도 보인다.
- 파일 이름: 원본 `보고서.md` → 수정본 `보고서 (수정 2).md`. 🔍 이름 규칙.
- ⏸️ 바뀐 곳을 색으로 보여주는 비교 화면(diff). 1단계는 도구 결과의 전/후 요약만.
- ⏸️ 수정본 버리기 버튼. 1단계는 다운로드만 (원본은 그대로 남아 있으므로).

## 7. 테스트

| 종류 | 내용 |
|---|---|
| 단위 | 정확히 한 번 일치 / 0번 / 2번 이상, 여러 수정 중 하나 실패 시 전부 취소, `replace_all` |
